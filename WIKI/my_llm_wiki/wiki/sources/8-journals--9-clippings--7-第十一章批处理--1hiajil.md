# 第十一章：批处理

本章系统介绍了批处理系统的概念、优缺点及其在现代数据处理中的角色。从单机 Unix 工具处理 nginx 日志的例子出发，展示了批处理的基本模式（读取、映射、排序、归约），并比较了内存聚合与排序两种方法的适用场景。内容扩展到分布式环境，详细解释了分布式文件系统（DFS）和对象存储作为批处理存储层的差异，以及资源管理器（如 YARN、Kubernetes）和工作流编排器（如 Airflow）在管理和调度分布式批处理作业中的核心作用与挑战。概述了 MapReduce 模型及其局限性，并指出了现代数据流引擎（如 Spark、Flink）作为其替代的演进方向。深入探讨了混洗（shuffle）算法，它是实现分组、连接、聚合的基础操作。讨论了高级查询语言（尤其 SQL）和 DataFrame API 如何让批处理作业更易编写，也更容易被优化器优化。最后回顾了批处理在 ETL、分析、机器学习和对外提供派生数据等场景中的常见用例，并总结了批处理系统的三层核心能力（编排层、存储层、计算层）及其与流处理的对比。本章末尾提供了 39 篇参考文献，涵盖 MapReduce、HDFS、YARN、Spark、Flink、Dryad、Nephele、BigQuery、Pregel、数据湖仓、数据网格等主题。

## 核心概念

- **批处理（Batch Processing）**：从只读输入生成派生数据的作业模式，通过重跑实现容错。
- **在线系统（Online Systems）**：以低延迟响应请求为目标的系统，与批处理相对。
- **派生数据（Derived Data）**：由原始数据通过计算（如批处理）生成的数据。
- **时间旅行（Time Travel）**：对象存储和开放表格式的一种特性，允许访问数据的历史版本。
- **分布式文件系统**：将文件分块存储在多个节点上，提供全局文件系统视图。
- **对象存储**：通过 HTTP API 存储和检索不可变对象的系统，以键值对方式组织。
- **MapReduce**：一种经典的批处理编程模型，包含映射、排序和归约阶段。
- **数据流引擎**：现代批处理框架，通过记录血缘和检查点实现高效容错和流水线执行。
- **工作流**：由多个作业通过依赖关系构成的 DAG，由工作流调度器管理。
- **资源管理**：在分布式集群中对 CPU、内存等资源进行分配和调度的过程。
- **混洗（shuffle）**：批处理系统的基础算法，用于实现分组、连接、聚合。
- **排序合并连接（sort-merge join）**：一种连接算法，利用排序后的数据简化分布式连接。
- **二次排序（secondary sort）**：在排序中进一步按次要键排序。
- **数据湖仓（data lakehouse）**：结合数据湖和数据仓库的架构。
- **批同步并行（BSP）**：图计算常用模型。
- **Pregel 模型**：图计算模型。
- **代价优化器**：分析连接输入特征，自动选择更合适的连接算法。
- **批量导入**：将批处理输出直接导入目标数据库。
- **冷启动与增量加载混合策略**：同时支持冷启动与增量更新的策略。
- **读已提交语义**：在收到完成通知前让新数据对查询不可见。
- **流系统作为缓冲层**：在批作业与生产库间充当缓冲层，避免影响线上流量。

## 关键主张

- 批处理通过回滚和重跑，能有效容忍人为失误，支持敏捷开发。
- 理解 MapReduce 是理解现代批处理框架的基础，尽管它已过时。
- 对象存储因其解耦计算和存储的特性，正取代 HDFS 成为批处理的主流存储层。
- 分布式批处理框架在功能和组件上可类比为一个"分布式操作系统"。
- 工作流调度器（如 Airflow）对于管理大型组织的复杂数据管道至关重要。
- 调度器中的资源分配问题是一个 NP-hard 问题，工程上常使用启发式算法。
- 数据流引擎能实现与 MapReduce 工作流同样的计算，但通常速度明显更快。
- 混洗是批处理系统的基础算法，连接与聚合都依赖它。
- 高级查询语言（尤其 SQL）和 DataFrame API 让批处理作业更易编写，也更容易被优化器优化。
- 批处理在"出错后排障与修复"方面很友好，这对调试数据流水线极其关键。
- 流系统可在批作业与生产库间充当缓冲层，避免影响线上流量。
- 批处理系统与云数据仓库正在收敛，两者越来越像。

## 关键证据

- **Unix 工具链实验**：通过使用 `cat`, `awk`, `sort`, `uniq`, `head` 等命令处理 nginx 日志，展示了批处理的核心逻辑，并证明其能高效处理 GB 级数据。
- **MapReduce 与 Unix 管道类比**：将 MapReduce 的 map、shuffle、reduce 步骤与 Unix 管道中的映射、排序、归约步骤直接对应，印证了 MapReduce 模型的设计渊源。
- **HDFS 与 S3 的对比**：分析了 DFS（支持原子重命名、链接）与对象存储（无目录结构、非原子操作）在功能和一致性上的差异，支撑了关于存储层演变的论述。
- **MapReduce 混洗实现**：详细描述了 MapReduce 中混洗的实现，包括 map 任务输出、reducer 连接、排序合并等步骤。
- **数据流引擎优势**：列举了数据流引擎相比 MapReduce 的多个优势，如减少 I/O 开销、优化数据局部性、支持流水线执行等。
- **批处理用例**：讨论了 ETL、分析、机器学习、对外提供派生数据等常见用例，并提供了具体实现方式。

## 矛盾与限制

- MapReduce 虽然带来了大规模数据处理的能力，但其编程模型原始、执行效率低，已被 Spark、Flink 等数据流引擎取代。
- 批处理虽然简单可靠，但其"全量重跑"模式在输入数据少量变化时效率低下，且输出无法被下游实时消费。
- 对象存储解耦计算存储带来灵活性，但通常不支持原生文件系统操作（如原子重命名），与 DFS 相比在某些场景有功能缺陷。
- 批处理与云数据仓库正在收敛，但并非所有批任务都容易用 SQL 表达，如 PageRank 等迭代图算法、复杂机器学习任务。

## 开放问题

- 如何在频繁任务抢占（如 spot 实例）的环境中，设计出比现有血缘重算或检查点更高效的容错策略？
- 在集群资源调度中，针对 NP-hard 的资源分配问题，能否提出比现有启发式算法更接近全局最优的实用方法？
