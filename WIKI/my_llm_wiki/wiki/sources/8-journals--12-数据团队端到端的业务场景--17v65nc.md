# 數據團隊端到端的業務場景：電商平台使用者流失預警系統

這份文件詳細闡述了數據團隊如何協作完成一個端到端的業務場景，以電商平台的「使用者流失預警系統」為例，從原始資料獲取到最終的智能化決策支援。

## 核心業務目標
降低高價值使用者流失率，從被動響應轉變為主動干預。

## 工作流與角色分工

### Phase 1: 資料基礎建設 (資料架構師 + 資料工程師)
*   **資料架構師產出**：[[資料分層設計]] (ODS, DWD, DWS, ADS 層)。
*   **資料工程師實現**：
    *   使用 [[Airflow]] 構建 [[ETL 管道]]，每日從 [[MySQL]]/[[MongoDB]] 抽取增量資料。
    *   在 [[Snowflake]] 建立 [[維度建模]] (使用者、商品維度表、事實表)。
    *   產出包含 120+ 特徵字段的 `dws_user_behavior_feature` 表。
*   **挑戰**：處理使用者跨設備行為合併問題 (ID mapping)。

### Phase 2: 探索性分析 (資料分析師)
*   **任務**：在 `dws_user_behavior_feature` 基礎上，透過 SQL 分析找到流失使用者的共性特徵。
*   **洞察**：流失使用者通常具有 30 天內購買頻次 < 2、客服接觸 > 3 次、優惠券使用率 < 10% 等特徵。
*   **產出**：《高價值使用者流失分析報告.pptx》。

### Phase 3: 報表自動化 (BI 開發者)
*   **問題**：業務方對報告的重複需求導致分析師手動操作不可持續。
*   **解決方案**：
    *   在 [[Tableau]] 搭建即時監控儀表板，包含 KPI、漏斗圖、細分分析。
    *   設定自動郵件，定期發送報告。
*   **技術選型依據**：選擇 Tableau 因業務團隊熟悉，培訓成本低；資料源直連 Snowflake 以保證即時性。

### Phase 4: 預測模型開發 (資料科學家)
*   **升級需求**：從「事後統計」升級到「提前 7 天預測誰會流失」。
*   **建模流程**：
    *   [[特徵工程]]：新增特徵 (如加購物車未支付次數)、定義時間窗口。
    *   [[模型選擇]]：嘗試 [[LightGBM]]、[[XGBoost]]、邏輯迴歸，最終選定 LightGBM (AUC=0.87, 召回率 78%)。
    *   [[模型可解釋性]]分析：透過 SHAP 值揭示客服投訴未解決是流失最強信號。
*   **交付物**：模型文件 (`churn_model_v1.pkl`)、特徵重要性報告、模型卡片。

### Phase 5: 模型生產化部署 (ML 工程師)
*   **挑戰**：將資料科學家在 [[Jupyter Notebook]] 中開發的模型轉化為可服務 10 萬使用者的即時預測系統。
*   **實現方案**：
    *   架構設計：Airflow 每日觸發特徵計算 → 特徵服務 (Feast/[[Redis]]) → 模型 API ([[FastAPI]]) → [[CRM 系統]] 消費預測結果。
    *   關鍵決策：使用 Redis 快取特徵 (降低延遲至 30ms)；模型使用 [[ONNX]] 格式部署 (推理速度提升 3 倍)。
    *   建立 [[A/B 測試框架]]：10% 流量驗證新模型。
*   **監控體系**：[[資料漂移監控]] (PSI 指標)、模型性能監控 (線上 AUC vs 離線 AUC)、業務指標監控 (干預使用者的次日留存率)。

## 角色協作的關鍵介面
文件詳細列出了資料工程師、資料分析師、BI 開發者、資料科學家和 ML 工程師之間交接環節的「關鍵產出物」和「常見摩擦點」，例如特徵定義不清、樣本偏差、Python 版本不兼容等。

## 流程演進路徑 (資料團隊成熟度模型)
*   **Level 1 (大多數公司現狀)**：工程師建倉儲 → 分析師寫 SQL → 業務方看 Excel。
*   **Level 2 (本案例)**：BI 自動化報表 + 預測模型輔助決策。
*   **Level 3 (AI Native)**：閉環自動化：模型預測 → 自動觸發行銷動作 → 效果回流再訓練模型。

## 總結
資料架構師定義規則，資料工程師構建管道，資料分析師探索洞察，BI 開發者實現自動化報表，資料科學家開發預測模型，ML 工程師將模型部署並運營。
