| 词   | 侧重点      | 常见来源             | 得到的东西    | 例子                  |
| --- | -------- | ---------------- | -------- | ------------------- |
| 启示  | 领悟、原则、方向 | 经历、失败、观察、他人观点    | “我明白了什么” | “反馈应尽早出现，而不是最后验收。”  |
| 灵感  | 创意、构想、办法 | 积累、联想、情绪、观察、偶然触发 | “我可以怎么做” | “用每周一次的回顾自动生成项目周报。” |

## 一个连贯例子

你发现某个 AI 视频处理脚本越来越难维护：

- 你得到的**启示**：工作流的核心问题不是模型能力，而是中间结果不可复现、失败后难以定位和重跑。
    
- 你得到的**灵感**：为每个任务创建独立目录，保存 `source.json`、字幕、摘要、日志和最终 Markdown，并给每一步加可单独重跑的命令。

前者是对问题本质的理解；后者是一个具体的设计方案。

## 细微差别

日常语言中两者可以并用，表示“思想上有收获，也产生了创造冲动”。但如果必须选一个：

- 想强调**人生/工作道理、认识改变、经验教训**：用“启示”。
    
- 想强调**创作点子、设计方案、技术实现思路**：用“灵感”。

“受到启示”比“得到灵感”更正式、更偏反思；“灵感来了”则更口语化，强调突发的创造性状态。


你听到的应该是 **spec-driven development**，不是 *spectriven development*。它读起来接近：

```text
spec-driven development
/ˈspɛk ˌdrɪvən dɪˈvɛləpmənt/
“斯佩克-德里文 开发”
```

其中 `spec` 是 `specification` 的缩写，意为“规格说明、需求规范、行为约定”。**Spec-Driven Development（SDD，规格驱动开发）**就是：先把软件“要做什么、满足什么条件、边界在哪里”写成清晰且可验证的规范，再让设计、任务拆分、代码和测试围绕该规范展开。 [ibm](https://www.ibm.com/think/topics/spec-driven-development)

## 核心意思

传统的随手开发常是：

```text
想法 → 直接写代码 → 遇到问题再补需求/补测试
```

规格驱动开发则是：

```text
目标与用户场景
→ Spec：需求、规则、边界、验收条件
→ 技术计划 / 架构约束
→ 可独立验证的小任务
→ 实现
→ 按 Spec 验证
```

因此，`spec-driven` 中的 `driven` 指“由……驱动、以……作为后续工作的依据”。Spec 不应是写完就被遗忘的文档，而是团队、测试和 AI coding agent 共同遵循的“事实来源”（source of truth）。 [github](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)

## Spec 通常写什么

好的 Spec 不必一开始就变成厚重的传统需求文档；它的关键是**明确、可检查、减少歧义**。常见内容有：

| 内容 | 示例：视频转录工具 |
|---|---|
| 用户目标 | 用户导入本地视频后，可以获得可搜索的字幕与摘要 |
| 功能行为 | 视频导入成功后，系统创建一个任务并显示进度 |
| 业务规则 | 音频时长超过 3 小时，先提示预计耗时并要求确认 |
| 输入/输出 | 输入：视频路径；输出：`transcript.srt`、`summary.md`、`metadata.json` |
| 错误处理 | ffmpeg 不存在时显示明确安装提示，不创建半成品结果目录 |
| 边界条件 | 路径有空格、无音轨、字幕已存在、任务中断后重跑 |
| 验收条件 | 给定一个 10 分钟 MP4，在成功完成后，生成带时间戳的 SRT 和 Markdown 摘要 |
| 非功能约束 | 本地优先；日志可追踪；任何步骤都可单独重试；不上传原视频 |

相应测试可以验证这些行为，而不只是验证“函数是否被调用”。

## 它和 TDD 的区别

两者可以配合，但不在同一层级：

| 维度 | Spec-Driven Development | TDD（测试驱动开发） |
|---|---|---|
| 主要问题 | 做的是否是正确的功能，规则和边界是否明确 | 代码实现是否正确、可回归验证 |
| 起点 | 用户价值、需求、约束、验收条件 | 一个会失败的小测试 |
| 工作单位 | 功能、用户场景、接口或系统行为 | 类、函数、模块或一个小行为 |
| 主要产物 | Spec、计划、任务、验收标准 | 自动化测试与实现代码 |
| 常见顺序 | Spec → 计划 → 任务 → 实现与验证 | Red → Green → Refactor |

例如 Spec 写“重复导入同一视频时，系统不应重复转录；应复用已有结果或提示用户选择”，这是产品/系统行为。之后你可以用 TDD 为 `jobId`、哈希去重、目录创建等具体逻辑写测试。

## Uncle Bob 语境

Uncle Bob（Robert C. Martin）说这个词时，通常是在谈 AI 编程带来的开发重心变化：过去程序员花大量时间把想法编码为实现；现在 AI 可以快速写出实现，但**人仍需要明确规格、约束行为、审查结果，并用自动化测试保证正确性**。

所以不要把它理解为：

> 写一段英文需求，然后不看代码地相信 AI。

更接近的是：

> 先让“正确应当是什么样”变得可表达、可测试、可追踪；再让 AI 或人类实现；最后以规格和测试验证，而不是以“看上去能跑”作为完成标准。

当前 AI 语境下，SDD 的含义仍在演变：较轻量的做法是“先写好 feature spec，再让 agent 协助实现”；更激进的做法则把规范视为主要长期维护对象，代码更多是由规范生成或反复派生出来的产物。 [github](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)

## 一句话理解

> **Spec-driven development = 先定义可验证的“应该怎样工作”，再写或生成“怎样实现它”的代码。**

这句话中的“启示”更接近英文 **heuristics**，不是前面日常语言里“某件事带来的领悟”。整句话对应 *Clean Code* 的原文：

> “You must gain the knowledge of **principles, patterns, practices, and heuristics** … and grind that knowledge into your fingers, eyes, and gut by working hard and practicing.”

意思是：你不仅要知道整洁代码的原则、模式、实践和经验性判断，还要通过反复写代码、阅读代码、重构和测试，把它们内化成近乎直觉的“代码感”。 [ptgmedia.pearsoncmg](https://ptgmedia.pearsoncmg.com/images/9780132350884/samplepages/9780132350884.pdf)

## 四个词分别指什么

| 中文译词 | 英文原词 | 指的是什么 | 例子 |
|---|---|---|---|
| 原则 | principles | 普遍的、较稳定的设计指导思想 | 单一职责、减少重复、代码应表达意图、优先可读性 |
| 模式 | patterns | 在反复出现的问题中，被验证有效的结构性解决方案 | Strategy、Adapter、Dependency Injection、Repository |
| 实践 | practices | 每天实际执行的工作方法和习惯 | 写单元测试、持续重构、小步提交、Code Review、命名清晰 |
| 启示 | heuristics | 经验形成的判断线索、检查准则或“经验法则”，不是绝对定律 | 函数太长通常值得拆分；参数太多常意味着缺少抽象；注释若在重复代码，优先改善代码本身 |

## 原则：判断方向的高层准则

**原则**回答的是：

> 写代码时，应该优先追求什么？在冲突时，按什么方向做取舍？

例如：

- 一个函数/类应尽量只承担一项清晰职责。
- 重复逻辑会带来重复修改和不一致风险。
- 代码被阅读的频率通常远高于被编写的频率。
- 依赖越少、边界越清楚，越容易修改和测试。

原则比具体语法更高一层。无论用 Python、TypeScript、C++ 还是 PowerShell，这些方向大多仍然适用。*Clean Code* 从命名、函数、注释、格式化逐步扩展到对象、错误处理、边界、测试、类、系统和并发等主题，正是在展示这些原则在不同层面的应用。 [sam-koblenski.blogspot](http://sam-koblenski.blogspot.com/2014/07/tech-book-face-off-clean-code-vs-agile.html)

## 模式：可复用的结构性解法

**模式**回答的是：

> 某类问题反复出现时，有没有一种已验证过、可命名和交流的结构？

比如你的转录/摘要工作流需要支持多个后端：

```text
WhisperLocalBackend
OpenAITranscriptionBackend
RemoteWhisperBackend
```

如果业务流程只依赖统一的 `transcribe(input) -> transcript` 接口，而不直接依赖每一种模型或 API 的细节，这就是 **Strategy（策略模式）** 的思路。

模式不是“看见问题就套模板”。它是一个共同语言：

```text
问题 → 适用条件 → 结构 → 好处 → 代价
```

例如依赖注入提升可测试性，但若一个小脚本只有一个明确依赖，为它引入大量容器配置，反而可能制造不必要复杂度。

## 实践：让原则变成日常动作

**实践**回答的是：

> 写代码的过程中，我具体应该怎么做？

它强调持续性，而不是读完规则后的“知道”。典型实践包括：

- 写完一个小功能就运行自动化测试。
- 改动功能时顺手去除附近明显的重复和坏命名。
- 把复杂条件判断提取为有业务含义的函数。
- 用版本控制把变更切成小而可审查、可回退的提交。
- 在 bug 修复前先构造能复现问题的测试或最小输入。
- Code Review 时同时看正确性、命名、边界与可维护性。

举例说，知道“函数应当短小”只是原则；每当 `process_video()` 同时做下载、转码、转录、摘要、写入 Obsidian、错误重试时，把它拆成边界清楚的步骤并添加测试，才是实践。

## “启示”其实是经验法则

译作“启示”容易让人误解。这里更准确的理解是：

> **heuristics = 启发式规则、经验性判断、代码异味检查线索。**

它不是形式逻辑中的定理，不表示“违反就一定错”，而是告诉你：

> 看到这个信号时，停下来检查：设计是否可能有问题？

例如：

| 经验线索 | 它提示的潜在问题 | 不是绝对规则的原因 |
|---|---|---|
| 一个函数有十几个参数 | 可能承担了过多职责，或缺少参数对象 | 底层库绑定、协议字段处理可能确实需要较多参数 |
| 注释在解释每一行做什么 | 名称、函数拆分或结构可能不够清楚 | 非直观算法、性能权衡和业务缘由仍应写注释 |
| `if/else` 或 `switch` 在多处重复 | 可能可用多态、映射表或策略对象消除分支 | 小范围、一次性的分支未必值得抽象 |
| 类名很难命名 | 类可能包揽太多职责 | 有时领域概念本来就复杂，需要先澄清业务模型 |
| 测试很难写 | 可能存在过强耦合、隐藏依赖或副作用 | 也可能只是测试环境和工具尚未配好 |

书中把许多这类“code smells and heuristics”集中整理在后面的章节：它们是审视代码的提示，而不是机械检查清单。 [sam-koblenski.blogspot](http://sam-koblenski.blogspot.com/2014/07/tech-book-face-off-clean-code-vs-agile.html)

## “成为本身具有的记忆”是什么意思

这里更自然的中文是：

> 通过长期练习，把这些知识“练进手指、眼睛和直觉里”。

不是死记“函数不能超过 N 行”，而是你读到下面的代码时，不需要逐项背诵规则，也会自然感到它有问题：

```python
def process_video(url, vault_path, api_key, retry, language, model,
                  output_format, embed_cover, timeout):
    ...
```

你会迅速察觉：

- 参数过多，接口可能没有表达清楚的任务边界。
- 下载、转录、总结、输出等职责可能混在一起。
- 认证、配置和业务逻辑可能耦合。
- 出错和重试策略是否有清晰归属？

接着再根据原则、模式和实践，决定是否该重构、怎样以最小成本重构。这种能迅速看出“哪里别扭、为什么别扭、可能往哪里改善”的能力，就是作者所说的代码感（code sense）。 [goodreads](https://www.goodreads.com/author/quotes/45372.Robert_C_Martin)

## 一句话记忆

> **原则告诉你追求什么；模式提供常见问题的结构解法；实践规定日常如何行动；启发式规则帮助你在真实代码中察觉可能的设计问题。**
