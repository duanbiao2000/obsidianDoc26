[[2026-09-15-故障笔记]]

如果从**软件设计哲学**来管理 Obsidian 单篇笔记的复杂度，我会把核心问题定义成：

> **不是“如何让一篇笔记变短”，而是如何让一篇笔记的认知边界保持清晰。**

你贴的这篇笔记其实已经出现了典型的 **complexity creep**：最初可能只是讨论“启示 vs 灵感”，后来不断吸收 `spec-driven development`、Clean Code、heuristics、principles/patterns/practices，最后变成了一个小型知识系统。

这不是坏事。真正的问题是：**这些知识之间的关系是否仍然可以被你的大脑低成本地导航？**

---

# 1. 用软件工程的类比看 Obsidian

可以把一个 Obsidian vault 看成一个软件系统：

|软件工程|Obsidian|
|---|---|
|Module|一篇独立笔记|
|Function|笔记中的一个局部概念|
|API|笔记标题 / 链接|
|Dependency|`[[另一篇笔记]]`|
|Interface|笔记对外提供的核心概念|
|Refactoring|拆分 / 合并 / 重写笔记|
|Code smell|一篇笔记开始承担太多职责|
|Architecture|整个知识库的结构|
|Documentation|笔记本身|
|Test|能否用自己的话解释 / 应用这个概念|

因此，**单篇笔记的复杂度问题，本质上和软件模块复杂度非常类似。**

---

# 2. 第一原则：Single Responsibility

软件里的：

> **一个模块应该有一个清晰的职责。**

放到 Obsidian：

> **一篇笔记应该有一个主要的认知职责。**

你现在这篇笔记大概有：

```text
启示 vs 灵感
      ↓
spec-driven development
      ↓
spec 是什么
      ↓
SDD vs TDD
      ↓
Uncle Bob
      ↓
principles / patterns / practices / heuristics
      ↓
代码感
```

这实际上已经不是一个概念，而是一个**概念树**。

可以问一个非常有用的问题：

> **如果我要给这篇笔记起一个非常准确的名字，它是什么？**

如果答案越来越困难，就是 complexity signal。

例如：

### Note A

```text
启示 vs 灵感
```

负责：

```text
启示
灵感
heuristics?
```

### Note B

```text
Spec-Driven Development
```

负责：

```text
Spec
SDD
TDD
AI coding
```

### Note C

```text
Principles, Patterns, Practices, Heuristics
```

负责：

```text
四个概念的区别
代码感
Clean Code
```

这样拆以后，并没有**减少知识**。

只是减少了：

> **一个节点同时承担多个职责。**

---

# 3. 但不要机械地“一概念一笔记”

这里非常重要。

如果你把 Obsidian 玩成：

```text
Principle.md
Pattern.md
Practice.md
Heuristic.md
Spec.md
Specification.md
SDD.md
TDD.md
...
```

你会得到另一个问题：

> **知识碎片化（fragmentation）。**

这就像过度拆分软件：

```text
UserService
UserServiceFactory
UserServiceFactoryProvider
UserServiceFactoryProviderRegistry
```

理论上非常 modular。

实际上没人想维护。

所以：

> **Modularity ≠ Maximum fragmentation**

真正的目标是：

> **High cohesion + low coupling**

---

# 4. 用两个指标管理笔记

这是我最推荐你建立的心智模型。

## Cohesion：内部是否属于同一个主题？

例如：

```text
Principles
Patterns
Practices
Heuristics
```

这四个东西本来就属于一个非常自然的知识单元。

所以：

```text
Clean Code — Four Layers
```

作为一篇笔记：

**High cohesion**

是合理的。

---

## Coupling：是否依赖太多外部概念？

假设一篇笔记变成：

```text
启示
 ↓
heuristics
 ↓
Clean Code
 ↓
AI coding
 ↓
SDD
 ↓
TDD
 ↓
knowledge management
 ↓
Obsidian
 ↓
Zettelkasten
```

每一个概念又链接出去。

最后你打开一篇笔记：

```text
A → B → C → D → E → F → ...
```

这就是：

**High coupling**

你的知识库会变成一个“知识 spaghetti”。

---

# 5. 一个非常好的判断规则：Depth vs Breadth

我建议你给每篇笔记设置一个隐形的：

> **中心概念 + 解释深度**

而不是：

> 中心概念 + 所有相关知识。

例如：

```text
                    启示 vs 灵感
                         │
             ┌───────────┴───────────┐
             ↓                       ↓
           启示                     灵感
             │                       │
       领悟/原则/方向             创意/构想
```

这很好。

但：

```text
启示 vs 灵感
      ↓
heuristics
      ↓
Clean Code
      ↓
SDD
      ↓
TDD
```

就已经跨越多个知识域。

**应该停止继续向横向扩张。**

---

# 6. 用“认知 API”理解一篇笔记

这是一个非常适合 Obsidian 的软件工程类比。

一篇笔记不应该让读者知道所有内部实现。

它应该暴露一个清晰的：

> **Cognitive API**

例如：

```markdown
# Spec-Driven Development

## Core Idea

先定义可验证的行为，再实现。

## Why

减少歧义、返工和 AI coding 中的错误。

## Workflow

Goal
→ Spec
→ Plan
→ Implementation
→ Verification

## Related

[[TDD]]
[[Software Requirements]]
[[AI Coding]]
```

这就非常像：

```text
public API
---------
Core Idea
Workflow
Related Concepts
```

而：

```text
为什么 Uncle Bob 这么说
各种历史背景
所有例子
所有争议
```

属于：

```text
implementation details
```

不一定需要全部塞进主笔记。

---

# 7. 你可以采用“渐进式复杂度”

不要一开始就决定：

> “这个概念必须拆成 5 篇笔记。”

而采用：

```text
Capture
   ↓
Simple Note
   ↓
Complexity appears
   ↓
Refactor
```

这和软件工程非常像。

### Level 1：Atomic

刚发现一个概念：

```markdown
# Heuristics

经验形成的判断规则，不是绝对定律。
```

够了。

---

### Level 2：Develop

开始出现：

```markdown
## Examples

函数参数过多
重复 switch
难以测试
```

---

### Level 3：Refactor

发现已经变成：

```text
Principles
Patterns
Practices
Heuristics
Clean Code
Code Sense
```

此时才拆。

---

# 8. 一个特别有价值的原则：Refactor when pain appears

不要为了“结构漂亮”而重构。

软件工程里：

> **Don't abstract prematurely.**

Obsidian 同样成立：

> **Don't structure prematurely.**

也就是说：

**不要因为理论上可能会复杂，就提前建立复杂结构。**

真正出现这些信号时再 refactor：

### Signal 1

你无法快速回答：

> “这篇笔记到底讲什么？”

### Signal 2

一个标题下面出现两个以上完全独立的问题。

### Signal 3

你发现自己不断写：

```text
“关于这个问题，另外还有……”
```

### Signal 4

一篇笔记开始拥有多个完全不同的结论。

### Signal 5

你经常只需要其中 20%，却不得不打开整篇笔记。

这时候就是：

> **knowledge code smell**

---

# 9. 最重要的不是长度，而是“概念跳跃数”

这是一个很容易被忽略的地方。

一篇笔记可以有 **3000 字而非常简单**：

```text
一个概念
→ 定义
→ 原因
→ 例子
→ 反例
→ 应用
```

也可以只有 **500 字却非常复杂**：

```text
A
→ B
→ C
→ D
→ E
→ F
```

所以：

> **复杂度 ≠ 字数**

更接近：

> **Complexity ≈ number of concepts × interaction between concepts**

尤其是：

**interaction between concepts**

才是真正危险的。

---

# 10. 一个很强的 Obsidian 原则：Keep notes boring

好的知识库其实应该有一点“无聊”。

例如：

```text
[[Spec-Driven Development]]
[[TDD]]
[[Heuristics]]
[[Design Principles]]
[[Design Patterns]]
```

每篇笔记都只解决一个问题。

复杂性被转移到了：

```text
links
```

而不是塞进正文。

这和软件设计非常类似：

> **复杂系统不是没有复杂性，而是把复杂性隔离在正确的边界里面。**

# 12. 最后给你一个 Obsidian 版的“软件设计哲学”

我会把它压缩成这 7 条：

```text
1. One note → one primary cognitive responsibility
   一篇笔记，一个主要认知职责

2. High cohesion
   笔记内部的内容应该天然属于同一问题

3. Low coupling
   不要让一篇笔记承担大量外部概念

4. Prefer links over embedding
   相关知识优先链接，而不是全部复制进来

5. Don't abstract prematurely
   没有痛点，不重构

6. Refactor when complexity becomes visible
   当认知负担开始出现时再拆

7. Optimize for retrieval, not storage
   知识库的目的不是“保存最多”，而是“最快找到并使用”
```

其中最后一条其实是最重要的：

> **Obsidian 不是数据库；它是你的第二认知系统。**

所以你管理的不是“笔记长度”，而是：

**attention cost → retrieval cost → comprehension cost → reuse cost**

一篇笔记如果让未来的你 **30 秒内理解它是什么、为什么重要、应该什么时候用**，它就是一个好的模块。

如果做不到，就该考虑 **refactoring**。
