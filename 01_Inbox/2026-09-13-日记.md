## strategic laziness
DietrichGebert/ponytail 

`DietrichGebert/ponytail` 的核心原则是：**不要先问“怎么实现”，而要先问“这件事是否需要实现”；一旦必须实现，就在能满足需求的最早层级停止。** 它把这种“懒惰资深工程师”哲学固化为一条从“不做”到“最小实现”的决策阶梯，目的是压制 Agent 的过度工程、无端抽象、重复造轮子和依赖膨胀。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

## 核心原则

它的主原则可以浓缩成以下四个：

1. **最好的代码是没写出来的代码**  
   对需求先做 YAGNI 判断：如果只是推测性需求、尚未出现的扩展点，应该不做，并用一句话说明不做的理由。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

2. **优先复用，而不是重新发明**  
   写任何新代码之前，先在当前项目找是否已有 helper、utility、type、已有模式或现有依赖可用。项目里几页之外已有的实现，不能因为 Agent 没查到就再造一个。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

3. **系统能力优先于第三方依赖，自带能力优先于自定义代码**  
   标准库优先；浏览器/操作系统/数据库等平台原生能力其次；最后才考虑项目已经安装的依赖。Ponytail 明确偏好 CSS 胜于 JS、原生 `<input type="date">` 胜于日期选择器库、数据库约束胜于应用层重复校验。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

4. **真正要写时，写最小且可工作的版本**  
   不要“顺便”抽象、加配置、补未来扩展点或引入新框架。若逻辑可一行写完，就一行；若不能，再写刚好满足当前需求的最少代码。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

## 懒惰阶梯

Ponytail 的关键机制是 **The Ladder**：每次写代码、改代码、重构、修 bug、设计 API 或选依赖之前，从上往下检查，并在第一个能解决问题的层级停止。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

| 顺序 | 要问的问题 | 约束与行动 |
|---:|---|---|
| 1 | **这真的需要存在吗？** | 推测性的需求直接跳过；不为“以后可能会需要”写代码（YAGNI） |
| 2 | **项目里已经有吗？** | 复用现有 helper、util、type、模式或组件；不要重写 |
| 3 | **标准库能做吗？** | 用标准库，不写等价工具函数 |
| 4 | **原生平台能力能做吗？** | 用 HTML/CSS、浏览器 API、数据库约束、操作系统能力等 |
| 5 | **现有依赖已经能做吗？** | 复用已经安装的包；简单逻辑绝不为此加新包 |
| 6 | **能写成一行吗？** | 可以就一行，不为了“看上去优雅”拆成多层 |
| 7 | **以上都不行？** | 才写最少的、当前能正确工作的自定义实现 |

注意第 2 层“复用现有代码”是它后来特别强调的部分：早期常见版本只有“YAGNI → 标准库 → 平台 → 已装依赖 → 一行 → 最小实现”，但当前主规则明确把“查项目并复用”放到标准库之前。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

## 可提取的硬约束

下面这些最适合直接拆出来，组合进你自己的 `AGENTS.md`、`CLAUDE.md` 或项目级 Agent 指令。

| 类别 | 可提取约束 | 实际含义 |
|---|---|---|
| 需求 | 不实现推测性需求 | 不为单一调用者造抽象，不为未出现的需求设计配置项、插件系统、多后端或泛型框架 |
| 代码库 | 修改前先搜索 | 新建 helper、封装或模块前，先 grep/搜索同类实现、既有约定和依赖使用方式 |
| 依赖 | 不为几行逻辑新增依赖 | 优先使用已有包；若标准库或少量代码即可解决，不加 npm/pip 包 |
| 抽象 | 不请求就不抽象 | 不主动加入 factory、strategy、repository、adapter、builder、event bus 等层 |
| API | 不设计“未来接口” | 不要预留未使用参数、flags、config、hook、extension point 或多实现接口 |
| 实现 | 最少改动面 | 只触及解决当前问题必需的文件、函数和调用点；不顺手重构相邻无关部分 |
| 代码长度 | 一行优先，但不牺牲正确性 | 只有清晰、可维护且无副作用时才压缩；不是把所有代码高尔夫化 |
| 依赖方向 | 原生能力优先 | CSS 优于 JS，平台 API 优于 polyfill，数据库不变量优于仅靠应用代码维护 |
| 审查 | Diff 最好的结果是更短 | 对 diff 审查时，专门找可删除的死代码、未使用灵活性、重复逻辑和过早抽象 |
| 技术债 | 有意的捷径必须可追踪 | 若为了简单而接受已知上限，要留下 `ponytail:` 注释，记录上限与未来升级路径 |

最后一条相当有价值：Ponytail 并不假装最简方案永远可扩展。只有当这是一次**刻意的、会留下已知能力上限的取舍**时，才用 `ponytail:` 标记；注释要指出限制以及何时、如何升级。例如全局锁是当前够用的方案，但吞吐量成为问题时改成按账户加锁。项目的 `/ponytail-debt` 会把这些标记收集成一个技术债清单。 [github](https://github.com/DietrichGebert/ponytail/commit/b6c04480c03e8db2f035751d7c46289779ec3362)

## 它反对什么

Ponytail 并不是普通的“代码质量规范”；它把审查范围故意收窄为**复杂度和过度工程**。其 `ponytail-review` 只找以下问题：

- 重造标准库或平台已有能力
- 没必要的新依赖
- 没有第二个实现却先抽象出来的接口
- 只有一个调用者却额外加的层
- 从未启用的配置项、泛化选项与“未来扩展性”
- 可以删除的死代码、无效灵活性或更短的等价实现

它明确把 correctness、security 和 performance 排除在这个专门的“减法审查”范围之外——那些问题应该走正常 [[code review]]，而不应借“极简”之名忽略。 [github](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail-review/SKILL.md)

## 建议提取版本

如果你不想完整安装插件，而想吸收它最有用的约束，下面是一个适合放进个人 `~/.claude/CLAUDE.md`、仓库 `AGENTS.md`，或改造成 Codex 指令的精简版：

```md
## Minimal implementation policy

Before writing or changing code, stop at the first option that solves the current requirement:

1. Does this need to exist now? If speculative, do not build it.
2. Does this repository already contain a suitable helper, type, pattern, or dependency? Reuse it.
3. Can the standard library solve it? Use it.
4. Can a native platform feature solve it? Prefer it over custom code.
5. Can an already-installed dependency solve it? Use it; do not add a dependency for simple logic.
6. Can the solution be a clear one-liner? Keep it one line.
7. Otherwise, write only the minimum correct code for the current requirement.

Constraints:
- Do not add unrequested abstractions, options, configuration, extension points, or future-proofing.
- Search the codebase before creating helpers or duplicating patterns.
- Keep the change set narrow; do not refactor unrelated code.
- Do not add a dependency if standard library, platform support, or a few clear lines solve it.
- Prefer deletion, reuse, and simplification over new code.
- When deliberately accepting a known scalability or correctness ceiling for simplicity, add a
  `ponytail:` comment that states the ceiling and the concrete upgrade path.
```

## 一个实用 AR Checklist

下面是一份适合你的技术工作、Obsidian vault、学习与内容制作工作流的版本。

### 1. 收集年度证据

先不要急着下结论，先把这一年的外部记忆线索找出来：

```markdown
- [ ] 浏览全年日历：会议、旅行、重要事件、深度工作周期
- [ ] 浏览照片与截图：地点、人物、生活片段、设备与工作现场
- [ ] 浏览 Obsidian 的 Daily Notes、Inbox、项目笔记和阅读笔记
- [ ] 浏览 GitHub、Git log、PR、issue、release 和本地项目目录
- [ ] 浏览 YouTube 观看/保存内容、转录项目、视频脚本与成品
- [ ] 浏览书单、文章高亮、语言学习记录和 Anki 变化
- [ ] 列出本年完成、放弃、暂停和持续推进的项目
```

这一层的目的只是让记忆变得具体。年度回顾最常见的误差是“只记得最近的事”和“只记得没做完的事”。

### 2. 回顾成果与经历

```markdown
- [ ] 我最满意的 5 个时刻、项目或成果是什么？
- [ ] 我学会了哪些可复用的技术、方法或判断？
- [ ] 哪些产出真正被使用、被分享或产生了外部价值？
- [ ] 我完成了哪些原本以为做不到的事情？
- [ ] 哪些关系、合作或对话值得记录？
- [ ] 哪些失败最终提供了重要经验？
```

注意：不必只写“大成就”。例如“建立了一条稳定的 Whisper → Markdown → Obsidian 工作流”可能比“看了多少视频”更值得记录，因为它改变了以后的能力边界。

### 3. 审查时间与注意力

```markdown
- [ ] 我的时间实际上流向了哪里？
- [ ] 哪些活动带来专注、能量和成长？
- [ ] 哪些事情持续消耗我，却没有明显价值？
- [ ] 我最常被哪些类型的信息、工具或任务打断？
- [ ] 哪些项目长期停滞？原因是范围过大、价值不明，还是缺少下一步？
- [ ] 哪些习惯或工具是真正有效的，哪些只是“看起来很生产”？
```

这部分很适合结合你的日程、Git 活动、Obsidian 统计、任务记录和使用过的自动化脚本来回看，而不是只凭感觉。

### 4. 回顾知识系统

```markdown
- [ ] 我的 Obsidian vault 中，哪些笔记成为高重力节点？
- [ ] 哪些项目笔记、MOC 或主题笔记最常被重新打开？
- [ ] 哪些 Inbox 内容从未处理，为什么？
- [ ] 哪些知识输入源值得保留、减少或取消订阅？
- [ ] 哪些视频、书、文章或课程真正改变了我的理解？
- [ ] 我是否保留了原始来源、链接、转录与证据，而不只是 AI 摘要？
- [ ] 哪些 AI 工作流节省了真实时间，哪些反而增加维护负担？
```

这部分对应 Nick Milo 与 Tiago Forte 视频中的一个重要思想：知识库的价值不在“存了多少资料”，而在于哪些材料被你反复连接、使用、表达和转化。

### 5. 回顾工具与技术栈

```markdown
- [ ] 哪些软件、插件、AI 服务或硬件真正融入了工作流？
- [ ] 哪些工具订阅、插件或脚本可以停止维护？
- [ ] Windows、PowerShell、WSL、Git、Obsidian 和编辑器之间有哪些摩擦？
- [ ] 哪些自动化值得重构为更健壮、可配置、可记录的脚本？
- [ ] 哪些工作流依赖云端、封闭格式或单一厂商，存在锁定风险？
- [ ] 我的备份、版本控制、密钥管理和隐私边界是否足够可靠？
```

这能防止“工具不断增加，系统反而更脆弱”的情况。

### 6. 提炼年度主题

```markdown
- [ ] 今年反复出现的 3 个主题是什么？
- [ ] 我真正想继续深化的方向是什么？
- [ ] 哪个方向只是外部期待或 FOMO，而非我的真实兴趣？
- [ ] 哪些东西需要停止、委托、自动化或降低标准？
- [ ] 明年我想保护的时间、精力与关系是什么？
```

这里可以使用“三项”作为反思容器，但不是为了修辞而硬凑三个词。若你最后发现只有两个主题，写两个就够；若有四个真正独立的主题，就写四个。

### 7. 转化为下一年行动

```markdown
- [ ] 写出 1 句话的年度方向，而不是一长串目标
- [ ] 选择 3–5 个值得推动的年度项目或领域
- [ ] 为每个方向定义“完成后世界有什么不同”
- [ ] 将年度方向拆成下一季度最重要的项目
- [ ] 为每个项目写下第一个 30 分钟内能执行的行动
- [ ] 设定下一次月度或季度 review 的日期
- [ ] 更新 Me.md、Vault Map、项目主页和必要的 AI 工作流说明
```

## 一个简短版本

如果你不想做完整年度回顾，可以用这 10 个问题：

```markdown
1. 今年最值得记住的 5 件事是什么？
2. 我完成、学习或创造了什么？
3. 哪些事情没有完成，真正原因是什么？
4. 什么持续带来能量？什么持续消耗能量？
5. 我的时间和注意力主要去了哪里？
6. 我真正使用过、值得保留的工具和系统是什么？
7. 哪些知识、项目或关系正在形成高重力？
8. 哪些承诺、输入源、订阅或项目应该停止？
9. 明年我想更靠近什么，而不只是想“完成什么”？
10. 下一季度最重要的一个项目，以及本周第一步是什么？
```

## 与 ARC 的对应关系

你可以将 `AR checklist` 记为：

```text
A — Appreciate the Past
回看、收集、珍惜具体经历

R — Reflect on the Present
找出模式、价值、能量与真实问题

C — Create the Future
选择方向、项目与下一步行动
```

所以当视频里说 `this AR checklist`，它指的通常不是待办事项式的“年终清理清单”，而是一个帮助你从资料、经历和过去一年中，重新建立 **人生全局视角（perspective）** 的结构化回顾流程。 [simonandschuster](https://www.simonandschuster.com/books/Life-in-Perspective/Tiago-Forte/9781668079973)
