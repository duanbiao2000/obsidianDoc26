模型变强, 会让入门那一段曲线变平缓, 因为你不用再写魔法提示词。但另一类学习成本反而上升了: 判断力、架构品味、验证能力和对失败的感知。从 Matt Pocock 的实践看, 门槛是从「怎么写 prompt」转移到「怎么当一个好的工程负责人」。这是我根据检索结果做的归纳, 不是他本人的原话。

## 变平缓的部分

* **提示技巧** : 不再需要精细的措辞, 模型自己能理解模糊指令。
* **工具调用与基础脚手架** : 这些部分越来越被模型和框架内置。
* **harness 的补丁** : 有文章建议换模型后重新评估, 只保留仍然有效的 harness 功能。 这说明旧的 workaround 会过期, 不过前提是你会做评估。 [hugobowne.substack](https://hugobowne.substack.com/p/how-to-build-an-effective-agent-harness)

## 没有变平缓的隐性曲线

**1. 上下文预算与「聪明区」。** Pocock 提出的「smart zone」大约在 140K token 以内, 超出后注意力下降、幻觉增多。 上下文窗口变大, 不代表可靠区间等比扩大。他的做法是把大任务拆成 spec, 再拆成每张都能放进一个上下文窗口的 ticket。 大多数人只关心窗口有多大, 不关心哪一段可靠。 [blog.alexrusin](https://blog.alexrusin.com/matt-pocock-skills-main-flow/)

**2. 对齐比生成更难。** 他的 `/grill-me` 让 AI 反复追问, 直到需求、边界条件都清楚, 再进入计划。 但这个技巧只有在你认真回答时才有效。他自己承认, 有时只是一路点头, 最后拿走了一个糟糕的计划。 这是一种需要训练的能力: 清楚知道自己要什么。 [nahornyi](https://nahornyi.ai/en/news/matt-pocock-claude-code-prompt-techniques)

**3. 反馈回路比提示词更重要。** 他的课程把 AGENTS.md 和反馈回路当作自主 agent 的约束, agent 能自主运行, 靠的是这些约束而不是聪明。 TDD 也被当作防止模型自由发挥的保险。 难点在于设计出让 agent 能自检的环境: 类型检查、测试、构建。 [nahornyi](https://nahornyi.ai/en/news/matt-pocock-claude-code-prompt-techniques)

**4. 代码库架构要适合 AI。** 课程明确教你设计 agent 能顺利工作的代码库, 并把软件架构视为自己的品味的一部分。 他还有一个技能专门找出可以深化的模块, 让代码更易测试、更便于 AI 导航。 很少有人把「让代码库对 AI 友好」当作一项要学的技能。 [aihero](https://www.aihero.dev/my-claude-code-cohort-a-teaser)

**5. 语言与领域知识的积累。**  `/domain-model` 把术语和决策沉淀到 CONTEXT.md 和 ADR, 让下一轮不从失忆开始。 模型没有跨会话记忆, 所以这些文档就是你的记忆系统。这与你的 Obsidian 知识管理有直接关系。 [nahornyi](https://nahornyi.ai/en/news/matt-pocock-claude-code-prompt-techniques)

**6. 流畅感造成的掌握幻觉。** 他的 `/teach` 技能提醒, 流畅会带来虚假的掌握感。 他管理多个 agent、每天上百次提交, 但先从零开始, 逐个文件地观察, 「先学刹车, 再踩油门」。 他还尝试过只写规格、不看代码的方式, 几个月后代码质量变差。 模型越强, 越容易让人放弃理解, 这是最危险的一条曲线。 [reddit](https://www.reddit.com/r/ClaudeAI/comments/1xat7xn/matt_pococks_claude_code_habits_5_takeaways_about/)

**7. 任务分配的判断。** 哪些适合让 agent 自主跑, 哪些必须人在回路里? 课程的划分是: 研究阶段要用你的品味, 原型用来探索设计空间, QA 计划用来保证代码合入前的质量。 判断错误的代价会随自主程度放大。 [aihero](https://www.aihero.dev/my-claude-code-cohort-a-teaser)

**8. 评估与 harness 的演化。** 换模型之后要用真实案例和稳定的评测集重新测试。 有研究甚至让 agent 自己改进自己的 harness, 而且不同基础模型会演化出不同的 harness。 也就是说, 最优配置因模型而异, 不能一劳永逸。 [hugobowne.substack](https://hugobowne.substack.com/p/how-to-build-an-effective-agent-harness)

## 需要保留的怀疑

* Pocock 的流程偏重, 有人在讨论里问, 每个 issue 花约一小时是否过度工程。 流程重量是否合适, 取决于项目复杂度。 [reddit](https://www.reddit.com/r/PiCodingAgent/comments/1t2tm5c/am_i_overengineering_matt_pococks_ai_coding/)
* 有评论者认为, 技能很难迁移, 最有用的是项目或组织特有、模型不知道的内容。 所以别照搬他的 38 个技能, 只保留对你有效的小序列。 [blog.alexrusin](https://blog.alexrusin.com/matt-pocock-skills-main-flow/)
* 以上多数来自博客、Reddit 和课程宣传, 可信度参差不齐, 没有严格的实证数据。

## 对你的启示

结合你的背景(Python/PowerShell 自动化、Obsidian、Anki 卡片流水线), 最值得投入的是三件事: 给每个脚本项目写 AGENTS.md 和 CONTEXT.md、设计可自动运行的测试和校验作为反馈回路、每次换模型后跑一组固定的评测任务。你刚才连续遇到 MuPDF、onnx 的编译失败, 也是一种隐性曲线: 环境和依赖的判断, agent 并不能替你完成。



## 对开发者的启示

结合 `2026-11-04-Ai学习过程中的隐形曲线.md`，关键变化不是“开发变得更便宜”，而是**成本从写代码转移到了定义、验证和承担风险**。

### 值得转变的思路

1. **从估算代码量，转向估算可交付结果。**  
   AI 能快速生成实现，但需求没说清、边界没想全，返工仍然要付费。预算先覆盖澄清需求、验收标准和失败条件。

2. **把验证当成开发的一部分，而不是收尾。**  
   测试、代码审查、集成、部署和回滚方案，不能因为“AI 已经写好了”就少算。生成越快，未经验证的改动也可能堆得越快。

3. **把人的判断力和注意力列入预算。**  
   判断方案是否合适、识别异常行为、决定哪些工作可以交给 agent，都需要工程师投入。AI 省下的键盘时间，不等于省下相同比例的项目时间。

4. **把“适合 AI 协作”视为工程资产。**  
   清晰的模块边界、自动测试、项目约定、领域文档和可重复的评测，会降低后续任务的沟通与验证成本。这些是前期投资，不应当作零成本背景。

5. **按风险而不是按 AI 使用程度分配自主权。**  
   可回滚、低影响的原型可以更自动化；涉及数据、安全、兼容性或核心架构的变更，要预留更多人工审查与验证时间。

### 今后做预算时，可以提前拆出这些项

| 预算项 | 要预估的工作 |
|---|---|
| 需求与方案 | 澄清范围、拆分任务、定义验收标准 |
| 实现 | 人工编码、AI 辅助生成、提示与上下文准备 |
| 验证与集成 | 测试、审查、调试、兼容性检查、部署 |
| 环境与依赖 | 安装、构建、权限、服务配置及环境问题 |
| 持续维护 | 文档、测试、架构调整，以及模型或工具升级后的复测 |
| AI 使用成本 | 订阅/API/算力费用，以及人工检查 AI 输出的时间 |
| 不确定性预留 | 需求变化、模型错误、未知依赖和返工 |

实操上，给每项工作分别估 **乐观 / 最可能 / 悲观** 三档；再按任务风险调整悲观情形，而不是统一套一个“用了 AI 就缩短 30%”的系数。优先记录实际的实现、审查、返工和环境耗时，几轮之后用团队自己的数据修正估算。

**一句话：预算要从“AI 能多快生成”，转向“把结果可靠地交付，需要多少人的判断、验证和返工余量”。** 文中提到的具体上下文窗口等数字和外部经验，适合作为提醒，不宜直接当作通用预算依据。
