这一条是我从访谈里概括出来的,并不是 Pocock 的完整论证。下面把它拆开讲,同时标明哪些是他说的,哪些是我的延伸。

## 为什么沟通是分水岭

他的出发点是,人和 agent 之间始终有一道沟通鸿沟:模型不知道你具体要什么、在乎什么,所以每次都得告诉它。 模型越强,执行的差距越小,而「说清楚要什么」的差距就越大。 [youtube](https://www.youtube.com/watch?v=Z8lf5oWKfj0)

另一层是,代码、测试、文档、提交说明都是语言。语言含糊的人,写出的需求、命名和接口也会含糊,agent 会忠实地放大这种含糊。「思维和语言的质量会体现在产品里」是我对他观点的概括,这类说法偏经验判断,没有实证数据。

## 「写清楚的变更报告」在练什么

这个例子本质上是练习三件事:

- **区分事实与判断**:改了什么、为什么改、影响哪里,三者分开写。
- **面向读者写**:读者是三个月后的你,或者一个没有上下文的 agent。
- **有取舍**:哪些重要、哪些可以略去。写不清楚,通常是因为没想清楚。

## 可以直接练的做法

1. **提交说明与 PR 描述**:固定写成「背景、改动、影响、如何验证」四段,每次都让 agent 起草,你来改。
2. **术语表**:他提到的通用语言,就是让代码、数据库、界面和对话共用同一套词。 你可以在 Obsidian 里为每个项目维护一页。 [youtube](https://www.youtube.com/watch?v=Z8lf5oWKfj0)
3. **先被追问,再动手**:用 grill 式访谈,逼自己把模糊需求讲成明确约束。 [youtube](https://www.youtube.com/watch?v=Z8lf5oWKfj0)
4. **复述检验**:让 agent 用自己的话复述你的需求,不对就改你的表达,而不是只改它的输出。
5. **英语学习的迁移**:你练英语表达的同时,可以试着用英文写变更说明。清晰地书写本身就是一种表达训练。

## 这个观点的局限

- 沟通好不等于技术强。更准确的说法是,沟通是放大器,而不是替代品。
- 「顶级开发者都善于沟通」是个人观察,可能有幸存者偏差。
- 过度写文档也有成本。Pocock 自己试过靠规格驱动开发,几个月后代码变差,最后放弃,回到关注代码本身。 所以清晰不等于冗长。 [youtube](https://www.youtube.com/watch?v=Z8lf5oWKfj0)
