# AGENT.md｜人物思想英文节目的持续协作协议

> 本文件是长期协作的操作宪章：它规定 Agent **如何工作**，不记录当天做了什么。
>
> 每次实质工作前必须先读本文件；当前状态、未决事项与下一步只见 `00-项目交接与实时状态.md`。

## 1. 文档职责边界

为避免同一内容被复制到多个文件，以下归属固定：

| 内容类型 | 唯一主归属 | 其他文件如何引用 |
|---|---|---|
| 导航、目录与入口路径 | `README.md` | 只链接，不承载规则或实时状态 |
| 长期工作方法、编辑底线、闸门、版本和交付规则 | `AGENT.md` | 不重复写进 README 或交接文档 |
| 当前版本、当前项目状态、未决事项、下一步、会话成果 | `00-项目交接与实时状态.md` | 不复述长期规则或正式内容正文 |
| 人物名单、编号、章节、入选理由、版本历史 | `人物库/100人候选名单-编排版-vX.X.md` | 交接文件只指向当前版本 |
| 当前人物库的可执行保留/排除约束 | `可复用资产/自动化/人物库硬约束.v0.1.json` | 仅供校验脚本读取，不保存编辑理由 |
| 人物/单集的研究、引文、事实和脚本 | 对应 `节目制作/EPxxx-人物名/` | 其他文件只链接，不复制材料 |
| 跨期方法、模板与任务 Skill | `可复用资产/` | 不将具体单集资料回写进资产库 |
| 机器检查事件与脚本 | `可复用资产/自动化/` | 不以脚本输出代替编辑判断 |

发生冲突时：**用户最新明确指令优先**；具体内容以其正式文件为准；发现引用不一致时，先修正式文件，再更新交接状态。

## 2. 不可改变的编辑契约

- 节目以英文口播为主、以高质量中文意译字幕辅助理解，服务北京、上海、广州等城市的知识型观众；
- **人是入口，思想是核心，现代处境是落点**：`One life. One tension. One idea worth testing.`；
- 不做人物百科、成功学复制、金句拼贴或单向造神；
- 每期只服务一个可检验的核心问题；强观点必须呈现边界、反例、修正或争议语境；
- 重要事实、引文和影响力说法必须可追溯，并准确区分人物自述、出版方说法、独立报道与节目解释；
- 不将中文材料反译成“人物的英文原话”，不让英文成为知识门槛；
- 用户已明确废弃的既有节目方向不得重新作为候选方案或资产提出。

## 3. 必经工作流与状态闸门

所有人物和单集遵循：

```text
RADAR → 选题评分 → B站新鲜度审计 → ERP/事实核查/版权初判
→ ERP GREEN → 叙事设计与英文逻辑脊柱 → 完整英文稿
→ 字幕/画面 → 录制剪辑/发布 QC → 复盘 → 可复用经验回写
```

- 未获得 `ERP GREEN`，不得创建或实质改写完整英文口播稿；
- 候选人物库不是排期表；只有通过选题和 ERP 才能建立正式单集；
- 正式 100 人名单必须保持机器约束配置规定的人数、编号、保留与排除状态；新增、移出或升级版本必须走 `person-pool-change` Skill；
- 对技术、创作者和表演者等特殊人物类型，必须调用相应的类型扩展 Skill；
- 研究、英文写作、字幕、画面、质检和发布的细则只见对应资产，不在本文件复制。

## 4. Skill 调度规则

每次任务先阅读 `可复用资产/skills/README.md`，只调用与工作类型匹配的 Skill：

- 正式人物库变更：`person-pool-change`；
- 新人物研究或 ERP 补齐：`episode-readiness`；
- 技术人物：在通用研究 Skill 后追加 `technical-person`；
- 创作者、演员、导演、音乐人、运动员、设计师：在通用研究 Skill 后追加 `creator-performer`；
- B站站内重复度与切口判断：`bilibili-freshness`；
- 完整英文稿：`english-script`，且仅在 ERP GREEN；
- 有实质变更的会话结束：`handoff-close`。

Skill 的职责是完成一种任务的输入、产出和验证；它不能推翻本文件的长期规则，也不能自行改变用户决定。

## 5. 自动化校验契约

自动化只做结构性、可机器判断的检查，绝不替人自动决定人物价值、资料可信度、版权可用性或 ERP GREEN。

- 事件与命令的唯一绑定表：`可复用资产/自动化/hook-manifest.v0.1.json`；
- 机器名单约束的唯一来源：`可复用资产/自动化/人物库硬约束.v0.1.json`；
- 当前运行环境中，Agent 按 manifest 在对应时点手动运行命令；迁移到支持生命周期 Hook 的运行时后，绑定同一批命令，不复制校验逻辑；
- `blocking` 检查失败时不得宣布相应工作完成；`warning` 检查需要人工判断和补充，但脚本不自动篡改文件；
- 每个校验脚本必须保持只读、基于标准库、输出具体失败原因。

## 6. 研究、平台与版权底线

- 回到原作、原始作品、论文、规范、系统文档、完整演讲/访谈和独立背景；短视频、营销文案、粉丝叙事和搜索摘要只能作为线索；
- 引文需保存原文、译文、归属、版本、页码/时间码和完整语境；
- B站“是否已有同类内容”只能由站内人工审计得出，外部网页搜索不能代替；
- 匿名当代场景需要授权、去识别化和必要的合成说明，评论或个案不能伪装成普遍数据；
- 优先自制图形、时间线、拍摄与合法素材；书页、影视/音乐片段、采访影像、代码、图片和截图须在使用前建立版权路径；
- 技术人物遵守 `16-计算机科学人物开发补充规范.md`；创作者与表演者遵守 `15-创作者与表演者人物开发补充规范.md`。

## 7. 每次工作的执行与收尾

### 开始

1. 读本文件；
2. 运行 `check_session_start.py`；
3. 读实时交接文件和任务对应的正式文件；
4. 选择所需 Skill；
5. 在做不可逆变更前，如用户意图不清晰则询问；一般执行细节不制造多余追问。

### 结束

1. 先更新实际发生变化的正式文件；
2. 运行与本次变更匹配的 `blocking` 校验；
3. 调用 `handoff-close` 更新实时状态、下一步和更新日志；
4. 若文件路径/版本变动，运行引用校验并同步导航；
5. 仅报告已完成、已验证、待确认或被阻塞的真实状态；
6. 呈现用户真正需要的主交付文件，而不是中间草稿。

## 8. 本文件的维护

只在长期方向、工作流、证据/版权底线、版本策略、Skill/Hook 体系或文档职责边界改变时更新本文件。

单集进度、每日材料、具体名单理由、页码、临时阻塞和下一步不写进本文件；它们分别归具体 EP、正式名单和实时交接文件。每次修改本文件都要更新 `last_updated` 并追加下方变更记录。
