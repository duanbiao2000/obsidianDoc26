# 16｜计算机科学人物开发补充规范

## 适用范围

适用于计算机科学家、软件工程师、编程语言设计者、系统建造者、网络/安全研究者、技术写作者等人物。

目标不是把节目做成技术史背诵，也不是用人物故事稀释技术。每期都要回答：

> **这个人面对了什么技术限制？他/她做出了什么设计选择？这个选择牺牲了什么、改变了什么？它又如何照亮我们今天的工作和生活？**

---

## 1. 技术人物的一手材料体系

| 类型 | 例子 | 用途 | 可信度要求 |
|---|---|---|---|
| **技术著作** | 教材、专著、技术散文、设计书 | 说明系统化思想与术语 | 取得合法版本；记录版次、页码与出版日期 |
| **论文/手稿** | ACM/IEEE 论文、作者手稿、技术备忘录 | 确认原创贡献与当时问题 | 回到正式发表版本或作者正式归档 |
| **规范/系统文档** | RFC、PEP、语言规范、设计文档、项目文档 | 解释设计决策与约束 | 优先项目官方仓库、标准组织或正式文档 |
| **代码/实现** | 可公开审阅的开源代码、历史版本 | 只在真正需要时说明实现证据 | 不将代码截图当装饰；标明许可与版本 |
| **完整口述材料** | 课程、主题演讲、技术对谈、长访谈 | 解释人物自己的判断与修正 | 优先完整录像/文字稿，避免切片断章取义 |
| **独立技术史/评论** | 大学、学会、技术媒体、同行回忆、传记 | 补充影响、争议与历史语境 | 至少一份独立来源，避免只使用个人自述 |

### 技术人物的最低研究包

- [ ] 1 本核心技术书，或 2 篇/组核心论文、规范、系统文档；
- [ ] 1 份完整技术讲座、课程或深度访谈；
- [ ] 1 条“设计决策 → 技术代价”的可视化链条；
- [ ] 1 份独立技术史/同行资料；
- [ ] 1 个今天仍可感知的应用或后果；
- [ ] 1 个边界、失败、争议或替代设计；
- [ ] 1 位具有相关背景的人完成术语事实复核（可为外部顾问或熟悉该领域的编辑）。

## 2. 技术解释的三层法

每个技术概念必须依次经过三层，不能只停在比喻，也不能直接掉进术语海洋：

```text
Layer 1｜生活语言：它解决了什么人的问题？
Layer 2｜系统语言：它在系统中如何工作？
Layer 3｜技术语言：关键约束、取舍或机制是什么？
```

示例（以“分布式系统中的一致性”为抽象例）：

- **生活语言：** 多个人同时改同一份文件时，怎样避免每个人都以为自己是对的？
- **系统语言：** 多台机器无法即时互相确认时，系统需要决定谁的记录可信、谁先等待。
- **技术语言：** 解释时间、消息延迟、状态复制和一个可视化的设计取舍；不需完整推导，但不能说成“电脑自动协调”。

### 旁白句式

- `The technical problem was not ____. It was ____.`
- `This design made one thing easier: ____. It made another thing harder: ____.`
- `A system is never neutral. It decides which failure is easier to live with.`
- `You do not need to write the code to understand the choice the code makes.`

## 3. 技术人物的叙事公式

```text
真实限制
  → 技术判断
  → 可观察的设计/著作/系统
  → 代价与反对意见
  → 对今天的技术与人的启发
```

### 不合格讲法

> “他发明了 X，所以改变了世界。”

### 合格讲法

> “在 X 造成的限制下，他拒绝了当时更容易的 Y，选择了 Z；这让某类协作变得可能，也让另一类问题更难处理。”

人物的性格只能作为解释线索，不能代替技术因果。

---

## 4. 对技术准确性的硬要求

1. 区分“提出概念”“实现系统”“推广生态”“撰写教材”四种贡献；不要全部叫作“发明”。
2. 不把协作成果全部归给一个人。明确合作者、团队、社区和前人的作用。
3. 不用今天的术语评价过去的设计，而不解释当时硬件、网络、成本和社会条件。
4. 不把一段代码、一个技术口号或一条名言当作完整思想。
5. 任何涉及安全、密码学、AI、隐私、操作系统、编译器、分布式系统的核心技术解释，都应有领域复核。
6. 无法向非专业观众准确解释时，删减范围，而不是以术语密度伪装深度。

## 5. 资料获取路径

| 需求 | 首选途径 | 补强途径 |
|---|---|---|
| 技术书/教材 | 正版纸书、电子书、公共/高校图书馆 | 作者主页、出版社页面、合法预览与引用数据库 |
| 论文 | ACM Digital Library、IEEE Xplore、arXiv、作者主页、大学机构库 | Google Scholar/Crossref 仅作检索入口，回到原文 |
| 规范/系统文档 | RFC Editor、语言/项目官方网站、官方代码仓库 | 标准组织档案、历史 release notes |
| 演讲/课程 | 大学课程页、会议官网、作者/机构官方频道 | 保留完整录像、演示文稿与时间码 |
| 技术史 | 学会奖项资料、大学档案、可靠传记、同行回忆 | 专业技术媒体和经过编辑的长访谈 |
| 术语复核 | 领域工程师、研究者、开源维护者或专业编辑 | 至少一人进行发布前事实检查 |

---

## 6. 视觉与版权

- 优先自制流程图、时间线、抽象系统动画和可复现实验；
- 代码只展示必要的 1–3 行或伪代码，且说明许可/出处；
- 不把 GitHub 页面、会议视频、公司发布会画面直接搬进成片；
- 设计图必须标出哪些是历史原图，哪些是节目重新绘制；
- 对仍在使用的产品界面，避免误导观众认为现行版本与历史版本一致。

## 7. 发布前技术绿灯

- [ ] 技术问题可用一句非术语语言讲清。
- [ ] 关键技术贡献有一手书/论文/规范/系统文档支持。
- [ ] 已写出至少一个明确的设计取舍。
- [ ] 已说明合作者、社区或制度条件，不造孤胆天才。
- [ ] 至少一个技术反例、边界或替代方案进入成片。
- [ ] 专业复核者已检查术语、人名、时间线和因果表述。
- [ ] 中文字幕术语和英文术语均进入项目术语表。
