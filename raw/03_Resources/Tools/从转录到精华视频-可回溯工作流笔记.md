# 从转录到精华版合成：可回溯工作流笔记

> 日期：2026-08-20  
> 场景：Windows 本地处理 YouTube 长视频；无 CUDA GPU，AMD 核显；目标是先转录、由 LLM 选精华片段、自动加章节标题并合成为 1080p 精简版。

---

## 1. 最终目标

对任意本地长视频完成：

```text
原视频
-> faster-whisper 本地转录
-> JSON 转录稿
-> LLM 生成 clips.json（保留片段与章节名）
-> FFmpeg 裁剪、缩放至 1080p、叠加章节标题
-> 合并全部片段
-> 写入播放器可跳转章节
-> 输出 highlights.mp4
```

最终成片有两层章节提示：

1. 每个片段开头约 4 秒的画面内中文章节标题
2. MP4 metadata 中可被播放器识别的 chapter

---

## 2. 本机环境与固定路径

### 硬件约束

- 没有 NVIDIA CUDA GPU
- 使用 AMD 核显，不能走 CUDA
- faster-whisper 必须以 CPU + int8 运行
- 原片为 4K AV1 时，最终精华版统一压制为 1080p，避免 CPU 负担与文件体积不必要地过高

### 已确认的工具与路径

```text
faster-whisper.exe
D:\Program Files\VideoCaptioner\resource\bin\faster-whisper.exe

模型根目录
D:\Program Files\VideoCaptioner\AppData\models

可用模型
faster-whisper-small
faster-whisper-tiny
faster-whisper-large-v3-turbo

日常转录默认模型
small
```

### 为什么选 small

用户已实际验证 `small` 对日常英文视频有足够好的正确率。CPU 转录下，优先保证可重复、速度合理；只在术语密集、音质差或最终字幕质量要求很高时，才考虑改用 `large-v3-turbo`。

## 3. 转录脚本设计

### 设计原则

- 默认只转录一个显式指定的文件，避免误处理整个目录
- 默认输出所有格式（`all`）而不是只输出 JSON
- 输出目录固定为视频同目录的 `_fw`
- 只有明确传 `-Batch` 或 `-Recursive` 时才进行批处理
- 默认 CPU + int8 + 英文 + VAD + 词级时间戳

### 日常命令

```powershell
transcribe ".\video.mp4"
```

例如：

```powershell
transcribe ".\I Connected Claude to My Entire Life (Here’s What Broke).mp4"
```

### 默认行为

```text
模型：small
设备：cpu
计算精度：int8
语言：en
任务：transcribe
VAD：开启
词级时间戳：开启
输出格式：all
```

### 输出文件

```text
视频目录\
├─ video.mp4
└─ _fw\
   ├─ video.json
   ├─ video.srt
   ├─ video.vtt
   ├─ video.tsv
   └─ video.txt
```

### 文件用途

| 文件 | 用途 |
|---|---|
| `.json` | LLM 选段、章节、摘要、后续自动化的主输入 |
| `.srt` / `.vtt` | 字幕、播放器、剪辑软件导入 |
| `.txt` | 人工快速阅读、检查识别错误 |
| `.tsv` | 以表格形式查看时间和文本 |

### PowerShell 命名冲突

最初尝试将命令命名为 `fw`，但 `fw` 已是 PowerShell 内置 `Format-Wide` 的 alias。因此改用：

```text
transcribe
```

这是更安全的命令名。

## 4. 转录时遇到的错误与修复

### 错误：PowerShell 变量后紧跟冒号

出现错误：

```text
Variable reference is not valid. ':' was not followed by a valid variable name character
```

原始代码：

```powershell
throw "Transcription failed with exit code $LASTEXITCODE: $($File.FullName)"
```

原因：PowerShell 将 `$LASTEXITCODE:` 误解析为带作用域的变量表达式。

修复方式之一：

```powershell
throw ("Transcription failed with exit code {0}: {1}" -f $LASTEXITCODE, $File.FullName)
```

这是更稳妥的格式化写法。

## 5. 从转录到 clips.json

### 工作原则

不要让 LLM 直接剪视频。LLM 的职责是根据转录 JSON 生成一个结构化、可审查、可修改的 `clips.json`；FFmpeg 脚本只执行这个清单。

这种拆分使每一步都可回溯：

```text
转录错误 -> 看 video.json / video.txt
选段错误 -> 改 clips.json
成片标题或编码问题 -> 改 Make-Highlights.ps1
```

### clips.json 的最小结构

```json
{
  "video_title": "精简版中文标题",
  "target_duration_minutes": 15,
  "clips": [
    {
      "order": 1,
      "title": "连接器不是万能记忆",
      "source_start": "00:01:24.000",
      "source_end": "00:03:41.500",
      "why_keep": "说明全片的核心问题与判断框架"
    }
  ]
}
```

### 时间格式规则

必须使用：

```text
HH:MM:SS.mmm
```

例如：

```text
00:01:24.000
00:41:54.500
```

### 推荐的 LLM 选段提示词

```text
你是视频编辑策划。以下是 faster-whisper 转录 JSON，包含时间戳。

目标：将原始视频剪成一条 12–18 分钟的中文标注精简版。
观众需要理解作者的完整逻辑链，而不是只看零散金句。

要求：
1. 选择 6–10 个片段，总时长目标为 12–18 分钟
2. 保持原视频的论证顺序；只有必要时才重排
3. 每段必须是连续原视频区间，尽量从完整句子或自然停顿处开始和结束
4. 删除寒暄、重复、广告、无关例子和低信息密度内容
5. 每段给出简短中文章节名，8–18 个汉字，适合叠加在视频开头
6. 标题要写清核心观点，避免“第一部分”“总结”等泛标题
7. source_start、source_end 格式必须为 HH:MM:SS.mmm
8. 不要虚构 JSON 中不存在的时间或观点
9. 只输出严格 JSON，不要 Markdown，不要解释

输出结构：
{
  "video_title": "精简版中文标题",
  "target_duration_minutes": 15,
  "clips": [
    {
      "order": 1,
      "title": "连接器不是万能记忆",
      "source_start": "00:01:24.000",
      "source_end": "00:03:41.500",
      "why_keep": "说明全片的核心问题与判断框架"
    }
  ]
}
```

### 编辑前检查清单

在运行合成前，人至少检查：

- 每个 `source_start < source_end`
- 时间是否从完整句子或自然停顿开始
- 是否删掉广告、寒暄和重复
- 是否保留完整的论证链，而非只保留“金句”
- 标题是否简短、具体、适合画面叠加
- `order` 是否连续且符合叙事顺序

建议第一次先做 2–3 个片段的测试版，而不是直接渲染 10 段。

## 6. Highlight 合成设计

### 目标

给定：

```text
video.mp4
_fw\clips.json
```

生成：

```text
video-highlights.mp4
```

### 每个片段的处理链

```text
原片时间区间
-> 输入端定位
-> 解码
-> scale=-2:1080
-> setsar=1
-> 片头 4 秒标题底板 + 中文标题 + 色条
-> libx264 + AAC 重编码
-> 输出独立的标准化片段
```

### 为什么不使用无损拼接

如果只裁剪和拼接，理论上可以 stream-copy，但本流程必须给每段加章节标题；`drawtext`、`drawbox`、缩放都是视频滤镜，所以需要重编码。

统一将所有片段输出为 1080p H.264/AAC 后，再使用 concat demuxer 以 `-c copy` 合并，可兼顾稳定性与效率。

### 1080p 输出策略

核心滤镜：

```text
scale=-2:1080:flags=lanczos,setsar=1
```

含义：

- 高度固定 1080
- 宽度自动按原始比例计算，且保证为偶数
- 4K 16:9 原片输出为 1920×1080
- `lanczos` 用于高质量缩小
- `setsar=1` 使输出以标准像素比例播放

### 标题样式

- 左下角
- 显示前 4 秒
- 白字、42px
- 黑色半透明底板
- 青绿色短横线
- 不长时间遮挡画面，只作为章节路标

## 7. Highlight 脚本的简化调用

最终将脚本设计为：视频是第一个位置参数；`clips.json` 可省略。

最短日常命令：

```powershell
highlights ".\video.mp4"
```

它自动查找：

```text
视频所在目录\_fw\clips.json
```

若要测试其他方案：

```powershell
highlights ".\video.mp4" ".\_fw\clips-test.json"
```

### `highlights.cmd` 包装器

建议保存到：

```text
C:\Users\danny\bin\highlights.cmd
```

内容：

```bat
@echo off
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Users\danny\.sh\Make-Highlights.ps1" %*
```

确保 `C:\Users\danny\bin` 已加入用户 `PATH`；重开终端后检查：

```powershell
Get-Command highlights
```

### PowerShell 会话说明

`pwsh -File` 会启动子进程来运行脚本。脚本结束后会自动返回原来的终端提示符，不需要手动 `exit`。

若单独输入 `pwsh` 才会进入一个新交互会话；这时用 `exit` 返回上一层 shell。

## 8. Highlight 合成时遇到的错误与修复

### 错误：FFmpeg filter graph 解析失败

典型报错：

```text
No option name near ...Windows...Fonts...msyh.ttc
Error parsing a filter description
```

根因：

- Windows 字体路径 `C:\Windows\Fonts\msyh.ttc` 的盘符冒号和反斜杠在 `drawtext` 中未正确转义
- 原先的 filter 字符串出现了多余反斜杠/等号
- 使用 `text_w` 试图在独立 `drawbox` 与 `drawtext` 间联动，在 Windows 环境下不够稳

修复原则：

1. 字体路径转换为 FFmpeg 形式：

```text
C\:/Windows/Fonts/msyh.ttc
```

2. 标题文本对反斜杠、冒号、单引号、逗号、百分号进行转义
3. 使用固定宽度的标题底板，而不是依赖 `text_w`
4. 先缩放，再画标题

### 清理重跑

若中间片段不完整或需要完全重做：

```powershell
Remove-Item ".\_fw\highlights-work" -Recurse -Force
highlights ".\video.mp4"
```

注意：这不会删除最终的 `video-highlights.mp4`；如果要完全覆盖最终成片，脚本里的 `ffmpeg -y` 会覆盖同名文件。

## 9. 产物与回溯路径

建议目录结构：

```text
视频目录\
├─ video.mp4
├─ video-highlights.mp4
└─ _fw\
   ├─ video.json
   ├─ video.srt
   ├─ video.vtt
   ├─ video.tsv
   ├─ video.txt
   ├─ clips.json
   └─ highlights-work\
      ├─ 001-章节标题.mp4
      ├─ 002-章节标题.mp4
      ├─ concat.txt
      ├─ joined-no-metadata.mp4
      ├─ chapters.ffmetadata
      └─ chapters.txt
```

### 发现问题时从哪里改

| 问题 | 优先检查/修改 |
|---|---|
| 文字识别错、漏词 | `video.txt` / `video.json`；必要时重新转录或改模型 |
| LLM 选错重点、章节名不好 | `_fw\clips.json` |
| 切点不自然 | `_fw\clips.json` 的开始/结束时间 |
| 标题位置、颜色、大小不满意 | `Make-Highlights.ps1` 的 `$vf` filter 部分 |
| 文件太大或太慢 | `-Crf`、`-Preset` |
| 章节时间不对 | `_fw\highlights-work\chapters.txt` 和 `clips.json` |
| 最终合并异常 | `_fw\highlights-work\concat.txt` 和逐段 MP4 |

## 11. 下一步改进点

### P0：先保证可靠性

1. **预检模式（强烈建议）**
   - 增加 `-ValidateOnly`：只读取 `clips.json`，检查时间格式、区间顺序、是否越过视频总时长、标题是否为空，但不渲染。
   - 增加 `-DryRun`：打印每个将执行的 FFmpeg 命令，便于排错。

2. **测试渲染模式**
   - 增加 `-Preview`：每段只导出前 8–15 秒，快速检查标题样式和切点。
   - 或增加 `-OnlyClip 3`：只渲染第 3 段，避免修改一个标题后重跑整片。

3. **媒体流自动检查**
   - 使用 `ffprobe` 获取视频时长、视频流和音频流。
   - 检查 clips 是否超出总时长。
   - 显式映射 `0:v:0` 和 `0:a:0?`，避免有封面流、数据流或多视频流时意外映射错误。

4. **输出覆盖保护**
   - 增加 `-Force`：只有显式传入时覆盖最终 `-highlights.mp4`。
   - 默认如果最终文件存在，则给出清晰提示而不是自动覆盖。

### P1：改善成片质量与效率

5. **转场而非硬切**
   - 目前片段间是硬切，适合知识内容，但可增加可选 `-Transition 0.25`。
   - 使用 `xfade`/`acrossfade` 实现 0.2–0.4 秒淡入淡出。
   - 注意转场会改变章节累积时间，需要脚本同步重新计算。

6. **标题安全区与自适应字号**
   - 当前底板宽度固定 1180，适合普通短标题。
   - 可加入标题过长自动换行、自动减小字体或生成两行标题。
   - 可提供 `-TitlePosition bottom-left / top-left`，避免遮挡说话人的脸或原始字幕。

7. **软字幕选项**
   - 可增加 `-Subtitle` 参数，将 faster-whisper 的 SRT 作为软字幕封装进最终 MP4。
   - 或增加烧录字幕模式，并设置可读样式。
   - 对 B 站观看和移动端理解很有价值。

8. **编码性能优化**
   - 当前 CPU `libx264` 稳定，但 4K AV1 解码和 1080p 重编码仍可能耗时。
   - 先检查是否可使用 AMD AMF 硬件编码：`ffmpeg -encoders | Select-String amf`。
   - 若 `h264_amf` 可用，可增加可选 `-Encoder amf`；默认仍保留 `libx264`，因为软件编码质量与兼容性更可预期。
   - 不建议盲目启用硬件编码：先渲染一个短片比较画质、速度、稳定性。

9. **缓存机制**
   - 使用片段开始/结束/标题/编码参数计算 hash。
   - 参数未变化时复用已渲染的片段，不必每次重编码。
   - 对反复修改 `clips.json` 的长视频项目可明显节省时间。

### P2：提升 LLM 与人工审校质量

10. **两阶段 LLM 工作流**
    - 阶段 A：只输出候选片段表，含时长、保留理由、叙事作用、风险提示。
    - 阶段 B：人工删改后，再让 LLM 生成最终严格 `clips.json`。
    - 可降低“LLM 一步到位选错片段后直接浪费编码时间”的风险。

11. **加入可审计证据字段**
    - 在 `clips.json` 增加 `evidence`、`first_words`、`last_words` 字段。
    - 渲染前让人快速核对转录开头和结尾是否与目标句子一致。

12. **叙事完整性评分**
    - 让 LLM 对每段标注：`hook`、`claim`、`evidence`、`takeaway`、`transition_note`。
    - 合成前检查精简版是否有开场、方法、案例、限制、结论，避免变成无上下文金句集。

13. **自动生成发布资产**
    - 从 `clips.json` 自动生成：B 站标题候选、简介、标签、置顶评论、章节列表和封面短文案。
    - 将发布信息保存为 `_fw\publish.md`，避免视频完成后重复整理。

### P3：扩展为可复用项目模板

14. **每个视频一个项目配置**
    - 增加 `_fw\project.json`：记录语言、模型、CRF、标题样式、目标平台、视频定位。
    - 之后只需执行一个命令，就能使用同一项目配置复现。

15. **一键总控命令**
    - 建立 `video-project` 命令：

```text
video-project video.mp4
-> 若无转录则转录
-> 检查 clips.json 是否存在
-> 若存在则 validate
-> 渲染 highlights
-> 导出 publish.md
```

16. **批量项目队列**
    - 对多个视频使用 manifest 列表，一次按顺序夜间渲染。
    - 每个项目独立输出日志、错误报告和可恢复状态。

## 12. 当前最推荐的下一步

按优先级执行：

1. 先让当前视频完整跑通 `highlights ".\video.mp4"`。
2. 人工观看最终精华版，确认标题、音频、切点、章节是否正确。
3. 先实现 `-ValidateOnly` 和 `-OnlyClip`，让之后的每个项目更安全、更快迭代。
4. 增加软字幕或烧录字幕；这是对 B 站可看性提升最大的下一项。
5. 最后再评估 AMD AMF 编码是否比 CPU x264 更值得使用。
