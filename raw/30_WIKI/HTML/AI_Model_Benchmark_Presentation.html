设计原则 测试方案如何设计？

  • 可路由：每道题对应一个真实生产场景，而非抽象智力题
  • 可判分：每题有明确评分标准（正确性 / 格式 / 推理 / 幻觉 / 可执行性）
  • 可复现：temperature=0、新建对话、关闭联网、重复 3 次取平均
  • 可执行：代码题必须实际运行；JSON 必须用解析器校验；工具调用必须模拟环境
  • 可分层：0-30% 不适合自动化 → 30-50% 需人工检查 → 50-70% 常规生产 → 70-85% 复杂任务需复核 → 85%+ 承担主要推理

⚠️ 版本声明

Luna / Terra / Sol 不是标准模型名称，不同平台可能指向完全不同的模型。本文档将其作为能力档位假设进行测试设计，而非能力结论。

评分体系 8 维评分 + 5 层分层

维度权重评分方式
正确性核心0-4 分
格式遵守高0-2 分（JSON/SQL/代码能否稳定解析）
推理完整性高0-2 分
信息真实性核心0-2 分（是否编造）
可执行性高0-2 分（代码/操作能否跑通）
响应耗时参考毫秒/秒
Token 消耗参考输入/输出
成本参考按 API 价格计算

生产环境最怕的三件事：偶发严重错误（最差表现）│ 格式不稳定导致解析失败 │ 任务失败类型不可预测

Luna 轻量通用任务测试

假设：适合客服、摘要、分类、改写、简单代码和低成本批量任务

典型题目

  • 信息抽取 → 合法 JSON 输出
  • 客服语气改写 → 礼貌、简洁、≤60 字
  • 条件判断 → 不混淆套餐/管理员权限
  • SQL 生成 → JOIN、聚合、日期范围
  • 代码修复 → 指出 bug + 说明复杂度

升级信号

  • 多步骤规划遗漏约束
  • 代码未实际运行验证
  • 不确定信息时过度自信
  • JSON/严格格式偶尔失效

适合：文本分类、信息抽取、摘要、客服改写、简单 SQL、大规模低成本任务

Terra 分析、长文档与知识组织

假设：适合复杂文档理解、跨段落关联、方案比较、风险分析

典型题目

  • 政策文档结构化 → 引用原文依据句
  • 多版本需求比较 → 追踪变化来源
  • 证据强度判断 → 区分相关性与因果
  • 时间线推理 → 发现流程倒置与返工
  • 合同风险归纳 → 标注低/中/高风险

升级信号

  • 只能摘要，不能跨文档建立关系
  • 引用内容与原文不一致
  • 长文档末尾信息明显遗忘
  • 对冲突资料强行整合

适合：长合同分析、多资料合并、需求评审、风险登记、管理层决策材料

Sol 代码、工具调用与任务编排

假设：适合工程代理、数据处理、API 调用、自动化流程和多步骤执行

典型题目

  • API 请求设计 → 幂等键 + 错误脱敏
  • HTTP 错误分类 → 重试/人工/失败策略
  • 并发代码改造 → 限制 + 隔离 + 顺序
  • 零停机迁移 → 扩展→回填→唯一→收缩
  • 退款 Agent → 状态机 + 幂等 + 审计

升级信号

  • 工具调用失败当成成功
  • 缺少幂等性设计
  • 代码未考虑并发和回滚
  • 对删除/付款/生产操作无审批意识

适合：API 编排、数据处理、代码修改、测试生成、Agent 状态机

Claude Haiku 快速低成本任务

定位：大量简单、短上下文、低延迟任务

✅ 适合

  • 批量分类 / 标签生成
  • 25 字以内短摘要
  • 简单规则推理
  • 格式转换（CSV/JSON）
  • 低风险信息抽取

❌ 不适合

  • 复杂代码修改
  • 长文档综合分析
  • 多步骤 Agent
  • 高风险金融/法律/生产操作
  • 复杂格式稳定输出
核心优势：高并发预处理场景下的性价比之王。

Claude Sonnet 通用生产任务

定位：复杂度中等的代码、分析、写作、文档处理和工具任务

典型题目

  • PRD 结构化提取 → Markdown 表格
  • 需求矛盾发现 → 实时同步 vs 离线可用
  • 代码审查 → 并发/一致性/回滚/资金安全
  • API 设计 → 分页/过滤/排序/幂等
  • 单体服务 90 天改造计划

何时升级 Opus

  • 需求本身高度模糊
  • 多领域知识同时参与
  • 需要长链条推理
  • 结果错误代价非常高
  • 冲突约束中做最终判断

Claude Opus 高难度推理与复杂决策

定位：复杂系统设计、隐含约束、长链条推理、批判性分析和高风险决策

典型题目

  • 跨区域支付系统 → 状态机 + 幂等 + 对账
  • 安全设计审查 → 提示注入/数据外泄/越权
  • 组织技术联合决策 → 5 组合并 4 套管道
  • 研究批判 → 指标偏差/因果谬误
  • 模糊目标实验设计 → 停止标准/干扰风险

红线：不能自动化

  • 生产环境破坏性操作
  • 法律/医疗/金融最终决策
  • 真实客户数据处理
  • 未经审批的权限变更

Opus 提供建议，执行必须人工审批。

DeepSeek-V4-Flash 高吞吐代码与推理

定位：低延迟批量代码任务、数学推理、中文处理、数据转换

典型题目

  • 中文结构化抽取 → JSON
  • 批量分类（10 条+ 边界案例）
  • 数学计算 → 折扣/优惠券/税费顺序
  • SQL 纠错 → GROUP BY 聚合修复
  • 区间合并算法 + 5 个边界测试

升级信号

  • 代码能写但边界测试不足
  • 复杂系统设计停留在组件罗列
  • 数学题只给答案无完整分支
  • 对重复/事务/幂等理解不稳定

适合：批量代码、SQL、中文分类、数学初筛、工程问题初步分析

决策框架 一条代码表达路由逻辑

if task.type == "classification" and task.risk == "low":
    use("haiku")

if task.type in ["sql", "code_generation"] and task.requires_execution:
    use("deepseek-flash")
    run_tests()
    escalate_if_failed()

if task.requires_long_context or task.has_multiple_documents:
    use("terra_or_sonnet")

if task.risk == "high" or task.has_conflicting_constraints:
    use("opus")
    require_human_approval()

if task.invokes_destructive_tool:
    block_automatic_execution()

→ Sonnet / Terra / Sol

模型档案 测试后应记录什么？

不要只记总分，要建立可追溯的档案：

基础指标

  • 版本 & 上下文长度
  • 平均耗时 & 成本
  • 输入/输出 Token

稳定性指标

  • JSON 稳定性
  • 代码可执行率
  • 长文档召回率

质量指标

  • 复杂推理得分
  • 幻觉率
  • 工具调用成功率

关键记录

  • 最差表现（偶发错误）
  • 失败类型分类
  • 升级到更强模型的条件

落地顺序 七步建立能力地图

  1. 用 10 道共同基准题测试所有模型
  2. 用专项题测试各模型特色能力
  3. 代码题接入真实运行环境
  4. JSON/SQL/工具调用进行程序化验证
  5. 用真实历史任务做第二轮回放
  6. 根据失败类型建立升级规则
  7. 每次更换模型版本后重新跑回归测试
最终得到的不是「哪个模型最聪明」，而是一张实用的能力地图：哪个模型在什么任务上便宜、快速、可靠，什么情况下必须升级，以及哪些动作始终不能交给模型自动执行。

从「模型排名」到「能力地图」

没有最好的模型，只有最合适的模型。

让正确的任务，在正确的成本下，交给正确的模型。
