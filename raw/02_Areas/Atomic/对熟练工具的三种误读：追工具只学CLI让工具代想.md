# 对熟练工具的三种误读：追工具只学CLI让工具代想

**核心**："熟练工具"常被误读为三件事——不停追新工具、只学命令行、让工具替你思考；三者都不是重点。正面标准是：这个工具是否让重要任务更快、更安全、更清晰或更可重复。

**为什么 / 证据**（三种误读 + 正面标准）：
### 误读一 · 不等于追逐工具
> "熟练工具"不是不停更换编辑器、终端、笔记软件或 AI 编程助手。工具越多不一定杠杆越大；若无法解释它减少了哪种错误、缩短了哪个反馈回路、替代了哪段重复动作，大概率只是生产力表演。
### 误读二 · 不等于只学 CLI
> 作者真正赞赏的不是"黑窗口文化"，而是 **composability（可组合性）**：小工具各做一件事，输出可被别的工具接收，拼成工作流。分界线不是 CLI vs GUI，而是操作是否可复现、可记录、可批量、可交给别人改造。
### 误读三 · 不等于工具替你思考
> 调试器、搜索、IDE、版本控制、AI 都能放大能力，也能放大混乱。你仍要定义问题、判断证据、决定验证标准；AI 的回答/脚本/补丁不等于通过真实环境与边界验证。
### 正面标准
> **Does this tool make an important task faster, safer, clearer, or more repeatable?** 这个工具是否让重要任务更快、更安全、更清晰或更可重复？

**边界 / 反例**：
- 可组合性可在 GUI 实现（如可视化工作流），CLI 不是充要条件。
- "更快"若以"更不可复现/更不清晰"为代价，不算达标。

**我的判断**（个人层 / 应用）：
- 我给任何新工具（含 AI 助手、笔记插件）都过这道标准：它让我哪件重要任务更快/更安全/更清晰/更可重复？答不出就不引入。这直接刹住我"看到新工具就想试"的冲动。
