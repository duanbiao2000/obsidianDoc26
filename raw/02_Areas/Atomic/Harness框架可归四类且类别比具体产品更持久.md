# Harness框架可归四类且类别比具体产品更持久

**核心**：业界 Harness 可按架构范式归为四类稳定心智模型：① 图/状态机驱动（显式控制流）② 极简代码即控制流（Code-as-Action，透明低层）③ 多智能体消息/事件驱动（协同对话、组织分工）④ 软件工程/环境沙箱驱动（终端反馈闭环）。具体产品更迭快，类别稳定，故只保留分类骨架。

**为什么 / 证据**（四类）：
- **图/状态机驱动**：把执行过程抽象为有向图/有限状态机，控制流显式写在代码里。
- **极简代码即控制流**：不被复杂封装遮蔽，核心骨架极简，行动即可执行代码。
- **多智能体消息/事件驱动**：多个 Agent 通过消息传递、协同对话或组织分工完成任务。
- **软件工程/环境沙箱驱动**：专注依赖环境反馈（终端/Bash/代码修改）的闭环。

（注：具体框架产品 LangGraph / smolagents / AutoGen / CrewAI / SWE-agent / OpenHands 等更迭极快、易过时，已按"丢弃易过时内容"原则不固化。）

**边界 / 反例**：
- 分类看似重叠（某框架可同时具"图驱动 + 多 Agent"特征），但四类应是**主控制流机制的正交侧重**而非互斥桶：每个框架按"主控制流"定主类，叠加能力记为次级标签（如 graph+multi-agent）。避免机械贴单一标签。
- 类别本身也会随技术演进重组；"四类"是可迁移的抽象，非永久真理。

**我的判断**（个人层 / 应用）：
- 我评估任何新框架先问"它落在哪类、解决哪类控制问题"，而不问"它叫什么、多火"。类别定位能跨版本复用，产品名字会过期。
