# Agent 应按触发条件动态路由到最匹配的技能画像

**核心**：给 Agent 定义一组技能画像（persona + 触发条件 + 输入上下文 + 输出风格），运行时按"触发条件"把当前请求动态路由到最匹配的画像，而不是用单一通用人格硬扛所有任务。

**为什么 / 证据**：
> Usage Guide for Agents: Read the `Trigger Conditions` and `Core Skill` of each block. Dynamically route the user's current request to the most appropriate skill profile.

单一人格在处理"写生产代码""深度研究""debug""产品原型"等异质任务时，要么过度泛化失去专业度，要么为全覆盖而臃肿。按触发条件路由，让每个任务落到最贴合的专长上（见 [[技能画像由人设触发条件输入上下文输出风格四要素构成]]、[[十类技能揭示的认知工作类型与维度]]）。

**边界 / 反例**：
- 路由本身需要判断"当前请求属于哪类"——这判断若做错，会落到错的人格。
- 技能过多会路由混乱、维护成本上升；技能过少则路由收益不明显。需平衡粒度。
- 多个画像触发条件重叠时不能靠"谁先匹配"，必须有一致裁决规则（见下方）。

**路由裁决规则**（修正重叠）：
1. **一级按意图分**：写新代码 / 修调试 / 审 / 设计 / 研究 / 原型 / 教 / 综合——八类意图互斥，先定主意图。
2. **二级按执行模式分**：在"写新代码"等意图内，再按 自主度（全自主↔交互式）与 关注点（权衡/可维护性↔速度/正确）细分。
3. **平局优先级**：写码意图内若仍命中多个——要全自主长任务→autonomous-coding；要实时结对→pair-programming；要资深权衡→production-engineering；三者皆否则默认 production-engineering（最通用写码角色）。code-review 属"审"意图，与其余写码角色天然互斥，不参与平局。

**我的判断**（个人层 / 应用）：
- 我给自己用的 Agent/工作流也采用这套：先判定任务类型（写码/研究/架构/debug/产品/综合），再切到对应模式。这比"一个万能助手"稳得多，也呼应我把默会判断显性化的做法。
