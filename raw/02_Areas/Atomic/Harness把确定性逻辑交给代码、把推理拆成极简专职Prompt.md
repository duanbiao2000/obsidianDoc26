# Harness把确定性逻辑交给代码、把推理拆成极简专职Prompt

**核心**：Agentic Harness 采用解耦策略——确定性逻辑（状态保留、循环控制、异常重试、API 解析、上下文截断）由代码严格控制；不确定的推理则拆成极简的专职 Prompt。

**为什么 / 证据**：
> 确定性逻辑归代码：状态保留、循环控制、异常重试、API 解析、上下文截断等由 Harness 严格控制。
> 不确定性/推理归 Prompt：单个 Prompt 被拆解为极简的专职任务（如"根据当前日志判断下一个调用的工具"、"总结本轮执行结果"）。

早期试图用"几千字万能 Prompt"解决复杂问题，极易幻觉或忽略指令；解耦后用代码兜底确定性、用 Prompt 只做该做的推理（见 [[Harness让代码掌控制权、LLM降级为循环内推理算子]]）。

**边界 / 反例**：
- 过度拆解会让 Prompt 碎片化，增加 LLM 调用次数与端到端延迟。
- "确定性 vs 需推理"的边界本身需要设计，划错位置会两头不讨好。

**我的判断**（个人层 / 应用）：
- 我的划界习惯：凡能写 if/else 或正则校验的，一律归代码；只有"理解语义、做判断、生成文本"才交给 Prompt。绝不用人话写校验逻辑。
