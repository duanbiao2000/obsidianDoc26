如果你**没有上游仓库的写权限**，又**不想 fork**，那就**无法提交标准 GitHub PR**。PR 的源分支必须存在于你有写权限的仓库中：要么是你的 fork，要么是上游仓库内的分支；而后者需要维护者授予你写权限。 [docs.github](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository)

## 两种可行路径

| 你的权限/意愿 | 可以怎么做 |
|---|---|
| 上游维护者给你写权限 | 建本地分支并直接推到上游，再在上游仓库内发 PR |
| 没有写权限且不 fork | 提 Issue，附上 commit / patch / 修改说明，请维护者采用 |
| 没有写权限但愿意 fork | 推送到自己的 fork，再发正式 PR（最标准）  [docs.github](https://docs.github.com/articles/creating-a-pull-request) |

## 不 fork 的做法

你现在最实际的选择是：在上游仓库开一个 issue，清楚说明问题、修复内容和验证结果，并附上你的 commit hash 或补丁文件。

先生成补丁：

```powershell
cd d:\MyVideos\yt-dlp\VideoCaptioner

# 查看你的本地提交 hash
git log --oneline -3

# 假设修复是最新的一条提交，生成可供维护者应用的补丁
git format-patch -1 HEAD --stdout > fix-windows-font-enumeration.patch
```

然后在 GitHub issue 中说明：

```markdown
## Bug
Windows 下字体下拉框仅显示 3 种字体，无法正确枚举用户安装的字体。

## Fix
修正 Windows 字体目录的枚举逻辑。

## Verification
- Windows 上启动 GUI
- 修复前：3 种字体
- 修复后：253 种字体

我已准备好补丁文件：`fix-windows-font-enumeration.patch`。
如果维护者愿意，也可以根据我提供的 commit 手动应用此修复。
```

你还可以把补丁上传到该 Issue（GitHub 支持将文件拖入评论编辑框）。维护者拿到后可以运行：

```bash
git am fix-windows-font-enumeration.patch
```

## 若要直接推上游

只有维护者明确把你添加为 collaborator / contributor，授予写权限后，才执行：

```powershell
git switch -c fix-font-enumeration
git push -u origin fix-font-enumeration
```

然后在上游仓库从 `fix-font-enumeration` 向 `master` 开 PR。没有写权限时，这个 `git push` 会被 GitHub 拒绝。 [coderefinery.github](https://coderefinery.github.io/git-collaborative/same-repository/)

因此，如果你希望修复**真正有机会被合入**，fork 并不是多余操作，而是 GitHub 为外部贡献者提供的正常权限边界；它不会影响你当前本地仓库，也不会让你的改动自动公开到上游。 [docs.github](https://docs.github.com/en/pull-requests/reference/pull-requests)
