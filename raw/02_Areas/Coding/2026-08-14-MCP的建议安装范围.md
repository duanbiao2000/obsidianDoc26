针对你列出的这 7 个 MCP 服务器，安装范围的建议可以总结为一条核心原则：**“通用知识类装全局，项目绑定类装项目”**。

以下是针对每个 MCP 的具体安装范围建议和理由：

### 🌍 建议安装为“全局 (User/Global)”的工具

这类工具提供的是**通用的知识库或跨项目的基础设施能力**，与具体代码仓库无关，在任何项目中都可能用到。

1.  **Context7**（强烈建议全局）
    *   **理由**：它是“最新的开发文档库”，覆盖海量框架。无论你在写 React、Vue 还是 Python，只要遇到库的用法问题都能用到它。放在全局可以避免在每个项目里重复配置。
    *   **配置建议**：全局加载，AI 会在需要时自动调用。

2.  **OpenAI Docs MCP**（建议全局）
    *   **理由**：专门用于查询 OpenAI API 官方文档。如果你经常开发 AI 应用或调用 OpenAI 接口，这是一个高频使用的通用参考工具。它与你的具体业务代码无关。

3.  **GitHub MCP**（建议全局）
    *   **理由**：管理 PR、Issue 和仓库元数据。这些操作通常是跨项目的（例如你在 A 仓库修 bug，需要去 B 仓库提 issue）。建议在全局配置好 GitHub 的 Personal Access Token，所有项目共享登录态。

---

### 📂 建议安装为“项目 (Project)”的工具

这类工具与**当前代码仓库的特定上下文强绑定**（如特定的设计稿、特定的测试环境、特定的线上项目 ID）。

1.  **Figma MCP**（建议项目）
    *   **理由**：它需要读取特定 Figma 文件的节点 ID 和设计稿数据。前端项目 A 和项目 B 的设计稿完全不同。建议在对应前端项目的根目录配置，方便团队共享 Figma 文件链接映射。

2.  **Playwright MCP**（建议项目）
    *   **理由**：自动化测试依赖项目的具体路由配置和登录态。为不同项目（如后台管理系统 vs 官网首页）编写的测试脚本和元素定位完全不同。放在项目级便于隔离测试配置。

3.  **Chrome DevTools MCP**（建议项目）
    *   **理由**：它的作用是在调试时连接当前项目的本地开发服务器（如 `localhost:5173`）。不同的项目端口不同，放在项目级可以配置具体的 `--browserUrl` 指向该项目的调试端口。

4.  **Sentry MCP**（强烈建议项目）
    *   **理由**：它需要绑定特定的 Sentry 项目 DSN 或组织 ID。如果你把项目 A 的 Sentry 配置装到全局，当你在项目 B 中调试时，AI 会错误地读取项目 A 的线上日志。**务必放在项目级配置，且不要提交包含敏感 Token 的配置**。

---

### ⚙️ 如何执行安装（以 Codex 和 Claude 为例）

- **Codex**：默认安装为全局（`~/.codex/config.toml`）。如果要安装为项目级，在命令后添加 `--scope project`。
  ```bash
  # 全局安装 Context7
  codex mcp add context7 -- npx -y @context7/mcp@latest

  # 项目级安装 Figma（需要在项目根目录执行）
  codex mcp add figma --scope project -- npx -y figma-mcp@latest --figma-token YOUR_TOKEN
  ```
- **Claude Code**：使用 `-s` 参数指定作用域。
  ```bash
  # 全局
  claude mcp add github -s user -- node github-mcp.js

  # 项目级
  claude mcp add sentry -s project -- node sentry-mcp.js
  ```

---

### 💡 关键提醒：避免上下文过载

虽然这些工具都很有用，但**不建议把所有项目级 MCP 都配置在全局**。如果全局加载了太多 MCP（如同时加载 Playwright、Chrome DevTools 和 Figma），AI 的上下文窗口会被这些工具的描述占据，导致处理速度变慢或上下文丢失。

- **通用准则**：把 Context7、OpenAI Docs 放全局作为“大脑”；把调试、测试和设计工具放在对应项目的目录下，按需加载。
