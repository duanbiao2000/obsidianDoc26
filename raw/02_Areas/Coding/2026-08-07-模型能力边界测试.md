下面给你一套可直接执行的模型能力边界测试方案。目标不是给模型做“考试排名”，而是判断：

- 哪些任务可以放心交给哪个模型
- 哪些任务需要人工复核
- 哪些任务必须升级到更强模型
- 哪些任务适合低成本批量处理
- 哪些任务涉及工具调用、长上下文、代码或复杂规划

先说明两个版本问题：

1. `Luna / Terra / Sol` 不是足以唯一确定具体模型的标准名称。不同平台可能把它们用于完全不同的模型。
2. `Claude Sonnet`、`Claude Opus`、`Claude Haiku` 需要固定具体版本，例如 Claude 3.5、3.7、4.x。
3. `DeepSeek-V4-Flash` 需要确认实际 API 供应商、上下文长度和发布日期。下文将它按“低延迟、高吞吐、代码和推理能力较强的 Flash 类模型”设计。

因此，下面对 `Luna / Terra / Sol` 的定位是测试假设，不是能力结论：

- Luna：轻量通用、日常文本和结构化任务
- Terra：较强分析、长文档、知识组织

# 十一、建议建立的模型档案

每个模型测试结束后，不要只记录总分，建议生成这样的档案：

```text
模型：
版本：
上下文长度：
平均耗时：
平均成本：
JSON 稳定性：
代码可执行率：
长文档召回率：
复杂推理得分：
幻觉率：
工具调用成功率：
最适合：
不适合：
需要人工复核的任务：
升级到更强模型的条件：
```

其中最重要的不是平均分，而是三个指标：

1. **最差表现**：生产环境最怕偶发严重错误。
2. **格式稳定性**：自动化流程中 JSON、SQL、代码能否稳定解析。
3. **任务失败类型**：是不会做、漏约束、编造事实，还是工具执行设计错误。

最终你会得到类似这样的路由配置：

```text
if task.type == "classification" and task.risk == "low":
    use("haiku")

if task.type in ["sql", "code_generation"] and task.requires_execution:
    use("deepseek-flash")
    run_tests()
    escalate_if_failed()

if task.requires_long_context or task.has_multiple_documents:
    use("terra_or_sonnet")

if task.risk == "high" or task.has_conflicting_constraints:
    use("opus")
    require_human_approval()

if task.invokes_destructive_tool:
    block_automatic_execution()
```

最稳妥的落地顺序是：

1. 先用 10 道共同基准题测试所有模型。
2. 再用上面的专项题测试其特色能力。
3. 对代码题接入真实运行环境。
4. 对 JSON、SQL、工具调用进行程序化验证。
5. 用真实历史任务做第二轮回放。
6. 根据失败类型建立升级规则。
7. 每次更换模型版本后重新跑回归测试。

这样得到的不是“哪个模型最聪明”，而是一张更实用的能力地图：哪个模型在什么任务上便宜、快速、可靠，什么情况下必须升级，以及哪些动作始终不能交给模型自动执行。
